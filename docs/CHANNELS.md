# Channels — Bud beyond the window

Date: 2026-08-31
Status: Telegram, Discord, and Slack shipped (You → Phone). WhatsApp / Teams / SMS
are declared with honest Later rows. Canonical constraints: `docs/GOAL-PROMPT.md` wins.

RealBud owns every channel. The worker stays per-turn and never knows a channel
exists: an inbound phone message becomes an ordinary Ask turn on the one Bud
thread, and the reply relays back out. A channel is a door to the same desk,
never a second agent, never a new nav place.

## The adapter contract

`server/channels/` holds one adapter per platform behind a shared shape:

- `verify(credentials)` → the platform answers who this bot is, or a
  plain-language throw.
- `start()` / `stop()` — inbound text in, relayed answers out.
- `status()` → the public shape for `GET /api/channels`: connected, platform
  identity, paired name, last message at. Never a token, never a raw chat id.

New pairings require a ten-minute, platform-specific code generated by the authenticated desktop settings page. Send the `/pair …` command privately to the bot. First contact without the code cannot pair or invoke Bud. Codes rotate on request and are cleared after pairing, reconnect or disconnect; only their digest is stored on disk. Existing paired accounts stay paired. Other chats cannot use the conversation. Credentials live in
`channel-<platform>.json` (atomic, 0600) and never appear in API responses or
logs. The poller never runs under VITEST and stops on server shutdown.

## Platforms

| Platform | Mechanism | Status |
|---|---|---|
| Telegram | Bot API long-poll over HTTPS | **Shipped** (`telegram.ts`, You → Phone) |
| Discord | Bot token verify via REST; inbound over the Gateway (native WebSocket, no dep); pair with the Mac code | **Shipped** (`discord.ts`, You → Phone) |
| Slack | Bot token (`xoxb`) via Web API; short IM poll by default; optional app-level token (`xapp`) enables Socket Mode (`apps.connections.open` + WebSocket) so a local Mac needs no public URL | **Shipped** (`slack.ts`, You → Phone) |
| WhatsApp | Cloud API is push-only: Meta calls a public webhook. A local-first Mac has no ingress without a tunnel/relay. | Declared (Later row). Needs a named office + named relay — do not build a tunnel silently. |
| Microsoft Teams | Bot Framework | Declared (Later row) |
| SMS | Provider account (Twilio or similar) | Declared (Later row) |

Non-text updates are out of scope until a platform proves itself. Media,
reactions, and parse modes are per-platform follow-ups, not the bridge.

## Hard rules

- One Bud thread. Channels never create bots, rooms, or agents.
- A channel answer is the same worker turn with the same boundaries: no send,
  no pay, approvals still land as cards.
- Phone-originated messages are tagged in Ask (`[Telegram · Name]`,
  `[Discord · Name]`, `[Slack · Name]`) so the transcript never hides where a
  message came from.
- Remote Allow/Deny is courtesy and owner wording only — never notices or
  licensee cards.
- Review cards show the recipient and full wording. Buttons and coded replies
  belong to that exact card and paired channel; edited, replaced, undelivered
  or pre-restart cards cannot approve current work. Bare yes/no asks for the
  card-specific response instead of making a decision. Wording too long for a
  complete phone card must be reviewed on Desk; it gets no phone approval buttons.
- Overlapping notifications coalesce. Failed delivery retains its card identity
  for recovery, and a notification failure does not undo an already saved
  decision. Allow approves wording for the PM to copy; it does not send it.


## Moving between phone and desktop (11 September 2026)

- On phone, `/continue` retrieves a bounded excerpt of the latest saved assistant reply from the active Ask conversation branch. It labels earlier output when Bud is busy. `/summary` returns a short deterministic handoff of recent turns (no model call). `/status` reports busy/available; `/help` explains the workflow. These commands require pairing and do not approve actions or change records.
- On desktop Ask, when a phone channel is paired, **Send to phone** pushes that reply and **Send summary** pushes the short handoff to the paired chat (`POST /api/channels/handoff`). Continue on phone can send the latest reply or summary the same way. A quiet activity stamp records the push in Ask.
- The conversation is one Bud thread either side. Phone-originated turns still relay replies back to the paired chat when the turn completes. Schedule jobs remain prepare-only in this wave — they do not auto-blast digests to messaging.
- On desktop, open Ask to review the same transcript and continue. Requests received while Bud is busy are saved before queueing. Newer waiting follow-ups replace the one waiting slot explicitly; both requests remain in the transcript. Restart preserves the request text; automatic channel dispatch and delivery recovery across restart are not claimed.
- At widths below 600px, labelled bottom navigation gives Desk/Ask/Schedule/You the full content width. This is responsive layout support, not remote browser access: the local API remains loopback-only. No tunnel, cloud relay or mobile app is created.
- Keep the Mac and RealBud awake and online for phone replies and handoffs. `/continue` can recover a saved reply after reopening the Mac; it cannot reach a sleeping or offline service. Messaging media uploads, a shared cross-device unsent draft, mobile notifications and independent phone execution remain unimplemented/unverified.
- Connecting a real channel may disclose Ask replies to the paired account. Confirm account ownership when pairing. Run real device acceptance with the intended account before describing the channel as live-office ready.
