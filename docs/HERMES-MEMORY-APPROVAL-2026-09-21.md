# Native memory approval boundary

Status: security fix integrated, independently reviewed, full source suite and unsigned macOS package verified on 21 September 2026. This package includes the bill-review recovery checkpoint. Current Windows and live-customer acceptance remain open.

## Problem and corrected behavior

Pinned Hermes 0.21.3 sends a foreground memory change through an ACP callback whose kind is `execute` and whose `command` is the memory text. RealBud previously interpreted that as a shell command. A preference beginning “git is our preferred change tracker” could match an existing `shell:git` rule. Driver full-auto and task-wide choices could also approve this durable change without a separate memory review.

The adapter now recognizes the exact admitted native callback envelope before shell/full-auto handling. Eligible single additions emit `hermes_memory_write`, a typed one-time policy and the complete bounded content. Missing, mismatched, oversized, control-character or credential-bearing input is refused before an actionable event exposes it. Unknown described callbacks, scripts and ambiguous operations also carry a hard one-time policy to the host. Only positively identified read/navigate/fill callbacks carry a separate provider-once classification. The host can refine that classification only after the existing reviewed job fence accepts the exact typed fields and the parsed destination hostname matches its origin. Script indicators in the original callback remain hard one-time even when a projected tool and URL look like navigation; malformed outside URLs cannot inherit the job origin. Both classifications still select the provider's allow-once option.

The host applies this policy before standing rules and automatic choices, omits reusable grant keys and excludes memory prose from browser/fence classification. Both response APIs bind to the exact live request card, reject rule expansion, require a complete review and force a one-time response. Existing stored memory permissions remain readable but inert; new memory rules and legacy saved bot grants are refused. Approval of memory does not create browser-action evidence.

The UI shows the exact content as literal, scrollable text, explains that it affects future conversations and offers one-time approval or denial. It cannot approve a missing/redacted preview. Session, task, portal-rule and Always-allow controls are unavailable even if an older client or saved card supplies them. Secret-bearing previews are omitted from persisted approval cards; denial remains available.

## Why additions only

Native replace/remove callbacks include a substring selector, not the complete existing entry they would alter. Native batches have the same gap. Showing that text as a complete review would be misleading. Those operations are currently refused, not silently approved and not claimed to be queued. A separate pending-memory review service must load the complete affected entry and bind approval to the exact current state before enabling them.

The pinned native store already rereads under a platform-specific file lock and writes atomically. The missing integration is a review with current/pending/profile/config digests and durable apply/decision recovery. RealBud business facts, source acceptance and payment authority remain outside worker memory. Private business backup continues to exclude worker memory, credentials and conversations.
