## Observed current behavior

- `server/customer-packs.ts:615,633`: proposal approval and reviewed revert stop at 100 inline versions per skill. `:149` also caps the entire `customer-packs.json` journal at 2,000,000 bytes. Large text, several skills or copied configuration snapshots can hit the byte cap first. Rejection preserves the active instructions/plans.
- `:156 completedUpgrade()` appends a new revision but reconstructs an override with only `activeRevision` and `versions`. Any new archive metadata must explicitly survive this function. `:169 journals()` and `server/private-workspace-backup.ts:146 validateBusinessFile()` independently admit live and backed-up overrides.
- `server/customer-pack-upgrades.ts:9 SkillOverride`, `:51 validatePackUpgradeState()`, `:148 previewPackChange()`: configuration snapshots copy overrides. A still-present current override wins during rollback; an absent/retired skill can recover an older snapshot override. A new published reintroduction can also start again at revision 1. Numeric revision alone is not a globally unique historical identity.
- `server/customer-packs.ts:550 proposals()` returns every inline revision including complete text. `:624 revertSkill()` selects only the current override's inline numeric revision; it appends a new revision through `:569 finishUpgrade()`, which pauses host schedules, clears plan approvals before file replacement, checks readback, persists completion and then removes the reviewed pending proposal. Original source/business records are untouched.
- `:85 validateCustomerPackArchiveSet()`, `:290 archiveChain()`, `:329 finishArchive()` already implement configuration archive integrity, saved-intent recovery, private storage, exact owned temporary-file cleanup and commit-before-prune. Reuse these patterns, not their configuration-specific schema or one-reference-per-batch assumption.
- `server/private-workspace-backup.ts:55 allowed(), :67 validatePrivatePackHistoryFiles(), :118 validateBusinessFile(), :175 filesAt()` and `server/private-backup-capture.ts:196 paths()` currently know only `customer-pack-history/<pack>/<digest>.json`. `server/private-backup-catalog.ts:442 seal()` invokes the shared graph validator. `server/private-backup-restore-catalog.ts:81 transformFile()` clears restored plan approvals and schedules; unknown ordinary admitted instruction files are copied exactly. Existing real v1/v2 integration fixtures are in `server/private-backup-pack-upgrade.test.ts`.
- `src/components/schedule/PackSkillReview.tsx:34` shows recent history and reviewed revert; `shared/customer-packs.ts:46 PackSkillRevision` lacks an archive/root selector. The UI currently advises service intervention at the cap rather than offering instruction archival.

## Recommended minimal design

1. Add a focused `server/customer-pack-skill-history.ts` pure schema/validator module. Use separate immutable content-addressed batches, for example `customer-skill-history/<pack>/<digest>.json`. Add an optional archive head to each `SkillOverride`, not just to the installation. A head carries digest, bounded batch/revision counts and a verified through-revision. A record carries pack/skill identity, prior head, bounded ordered versions and audit metadata. Active revision and complete active text remain inline; retain the two newest inline versions. Archived versions remain reachable and readable, with no silent deletion or renumbering.
2. Keep old unarchived journals and backup payloads readable. Introduce an explicit journal format/capability gate when the first skill archive is committed (a v2 root with existing v1 entries is the simplest candidate). Old code currently tolerates extra override keys and `completedUpgrade()` would drop them; therefore merely adding an optional head is unsafe for a later downgrade. An older application must reject an archived journal rather than mutate it while losing references. Persist that root marker thereafter; inspect every journal writer and backup validator.
3. Reuse the shared `packWriters` lane. Preview binds pack ID, installation generation/digest, skill ID, exact hot versions and head, active revision/digest and trusted workspace/profile/workroom scope. Archive only canonical history; preserve and surface a recovery error for previously admitted ambiguous ordering/duplicate revisions. Persist a compact exact intent, write/readback/fsync the immutable file and directories, then atomically publish the new head plus shortened hot list. Preserve active file bytes, active revision, recipe revisions, approvals and schedules. Hold conflicting changes/preparation while intent exists. Identical retries reconcile against saved intent/receipt, including after restart or a lost reply. Never rewrite a foreign/conflicting file or remove unproven temporary content.
4. Reserve bounded metadata headroom for near-full legacy journals. A compact intent must not duplicate version text. Prefer a narrowly validated allowance (for example at most 16 KiB only for a valid skill-archive intent over an otherwise <=2,000,000-byte journal); normal completed journals retain the current 2 MB bound. Both old and completed states must pass preflight. Do not generally raise limits, silently prune proposal receipts or add an unguarded sidecar. If the selected archive cannot relieve the whole-journal limit, show its exact remaining blocker and preserve data; existing configuration archival remains a separate available action. This does not solve unlimited proposal-receipt growth.
5. Browse archived revisions in bounded pages pinned to a selected configuration's exact skill head. Fetch complete selected text for review on demand. Bind revert preview to current installation generation, current active revision+digest, source head and target revision+digest; a content hash alone misses A→B→A and numeric revisions can be reused after removal/reintroduction. Confirmed revert reuses the existing durable approval-clearing upgrade path, appends a new current revision and explicitly preserves archive heads. Original immutable configuration archives are never rewritten to retrofit this feature.
6. Extend the common backup graph admission to walk all roots: current overrides, recent configuration snapshots and every archived configuration snapshot (plus transition roots for live consistency; backup rejects any pending mutation). Deduplicate a shared immutable skill batch by canonical path/digest, but separately detect cycles along each traversal and validate every root's counts/identity. Repeated valid references are legitimate; foreign identity, missing referenced files, detached files, invalid counts, wrong digests and unrecognized storage entries fail closed. Traverse one bounded batch at a time, with total graph budgets; never load all full history text into the UI/runtime.
7. Restore copies instruction bytes and history references exactly and retains existing approval/schedule invalidation. Old audit scope in immutable batches is provenance, not destination execution authority; new mutations bind the destination scope. Restored native worker files continue through existing repair/review; an archive never provides execution permission. Use the same two-level portable directory shape as configuration archives (a separate 80-character skill directory could exceed the existing 240-character portable-path cap). Add the new directory/path rules to both v1 and v2 capture, target/removal enumeration and prepared-restore admission through their shared helpers.

## User-visible outcome

The instruction review panel offers “Archive older revisions” before the limit blocks work, shows what stays immediately available and what moves to retained history, and states that current instructions and plan approval do not change. It displays pending archival recovery with an exact “Resume archival” action. Users can browse old versions and compare complete text before reverting; a revert still explicitly pauses plans and requires fresh approval. Stale previews/pages refresh, interrupted/unknown outcomes reconcile, and damaged history is held with existing bytes preserved. No provider, Hermes core or website-command capability changes are needed.
