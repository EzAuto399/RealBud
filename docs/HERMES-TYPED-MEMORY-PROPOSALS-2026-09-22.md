## Outcome and ownership

An ordinary Product Ask conversation can prepare an exact typed add, replacement, removal or atomic single-target batch for Bud's conversational preferences. It cannot apply or approve that change. The existing Settings review presents the complete before/after text and owns the human decision. Business records, agency settings, financial sources, work permissions and vendor credentials remain outside preference memory.

The implementation reuses RealBud's authenticated loopback MCP pattern and the admitted unmodified Hermes store. It avoids interpreting the ambiguous native replacement/removal/batch permission prose as a complete change. The existing native single-add once-only approval route remains independently guarded.

## Contract

- One MCP server, `memory-proposals`, exposes only `memory_propose`. Input contains a bounded request ID and a strict native-shaped payload. Aliases, identities, paths, keys, review digests and decision fields are refused.
- The host binds workspace, worker profile, admitted runtime and conversation. A current active turn and reasoning entitlement are checked at execution and replay. Warm conversations reuse a broker only within the same host scope and use the current turn's callback. Settling/cancelling a turn aborts in-flight work; disposal revokes the broker.
- The model receives only a proposal ID and the location of the human review screen. A returned ID is not proof that memory was applied. Callback failures use fixed messages without private error text.
- The host-only service re-enters the captured worker profile, checks current ownership before and after asynchronous work, participates in workspace restore admission and drains owned helpers before releasing their profile mutex. There is no renderer proposal-creation endpoint.
- Native publication must have durable request identity, exact payload conflict detection and no-clobber publication. A lost reply must not create another proposal, and replay after human completion must not recreate pending work. Signed metadata receipts do not contain preference text; private temporary staging files may contain the pending payload.

Publication uses a signed prepared journal, a private fsynced stage, a no-clobber hard link into native pending storage, removal of only the private stage, and a signed published journal. Recovery admits only the exact two known paths to the same private inode; the general native file reader still rejects hardlinks. A matching human-decision receipt completes proposal bookkeeping after a crash without restaging or applying memory. Conflicting bytes, missing published work without a receipt, foreign replacements and invalid journals are held for recovery. Directory and request limits are bounded; journal history is not silently evicted.

The actual Ask integration uncovered and fixed two profile-producer defects: atomic policy replacement had widened file permissions, and creating missing YAML 1.1 sections with `setIn` produced `!!omap`, which upstream PyYAML reads as a sequence. New/repaired policy files use mode 0600, newly created profile directories use 0700, and missing learning sections are explicit plain mappings. Startup still preserves existing installed profiles; no blanket migration or permission rewrite is performed. The packaged YAML vendor includes the required `YAMLMap` export.

Typed proposals retain the supplied literal text. The review preview follows admitted native semantics: Hermes trims entry-edge whitespace while retaining interior spacing. The full resulting bytes are shown before the person approves.

The typed path is held on Windows until per-file ACL and durable native publication are admitted there. A private directory alone is insufficient proof for existing files with explicit grants. Same-OS-user/admin tampering is not prevented by these local filesystem checks.
