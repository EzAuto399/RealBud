# Updates that install themselves, 10 October 2026

**This does not establish:** an installed upgrade on a customer PC, a Mac update (Mac builds aren't released), or customer acceptance.

The owner asked on 10 Oct 2026 for RealBud to restart itself to update, covering the everyday cases, retiring old versions and the edge cases.

## What went wrong on Kevin's PC (10 Oct)
- **Stuck on 0.1.48 after 0.1.50 shipped.** It downloaded 0.1.49, and `check()` then stops checking while an update is downloaded (`electron/updater.mjs:46`). 0.1.50 was never seen.
- **Nothing installs unless someone clicks.** `autoInstallOnAppQuit = false`, and no restart happens by itself until the first click. The PC kept the 0.1.48 Redbark bug that 0.1.49 fixed.
- **The click can lose work on Windows.** `quitAndInstall` starts the installer before `app.quit()`. If "Keep your unsaved work" then cancels the quit, the installer is already running.

## Product, user, job
- **Product:** RealBud keeps itself on the newest version, and nobody loses work to an update.
- **User:** office staff on Windows PCs that stay on all day. Their RealBud is often open but idle.
- **Job:** be current without thinking about it, and never be interrupted mid-task.

## Happy path
1. A check finds a newer version. It downloads in the background, even if an older update is already waiting; the newest replaces it.
2. The status bar shows "Update ready · restarts when you’re away". A dismissible card names the version and offers "Restart now" and "Later".
3. RealBud waits for a safe moment (below). If the screen is locked it installs at once. Otherwise it shows "Restarting to update in 60 s" with "Restart now" and "Not now"; any keyboard or mouse use cancels the countdown.
4. RealBud stops its office service, installs and reopens on the new version.
5. The first launch on the new version shows "Updated to 0.1.51" with "What’s new" (the release page), once.

## Safe moment (all must hold)
- An update is downloaded, and "Later" isn't holding it.
- No keyboard or mouse use for 5 minutes, or the screen is locked.
- The window has no unsaved work. Main asks the renderer, which answers from the same checks as `beforeunload`.
- The office service isn't busy. Busy covers an Ask turn, a scheduled run, a bank import or REI refresh someone started, a browser or portal task and Bud setup.
- Nothing is waiting on the person that a restart would drop: an approval card, a step of a bank import or REI refresh, an REI list preview not yet saved, or a person's own REI sign-in. Once the update is required this no longer holds it, so a forgotten card can't keep a PC on an old version. The restart ends that card, and the step has to be asked for again.
- A scheduled run waiting for REI sign-in, or a bank import waiting at sign-in, doesn't hold the restart. Both are saved and pick up again after the restart, so counting them would keep a PC off the new version all day.

Checked every minute while an update waits.

## Later and required updates
- **Later** holds the automatic restart for 4 hours. The hold is kept on disk, so it survives a relaunch. "Restart now" always stays available.
- **Required** means "Later" goes away and a waiting approval no longer holds it; the update still waits for the person to be away, and never cuts unsaved work or a running task. An update becomes required when:
  - it has waited 24 hours since it downloaded; or
  - the running version is below `minimumVersion` in `latest.yml`. The release step can add that line by hand; electron-updater keeps unknown keys. The card then reads "This version is no longer supported".

## One ledger of work (11 Oct)
Two reviews kept finding work the restart checks missed: person-started bank imports, then cards. A survey on 11 Oct then found manual job runs (the path all workflow-pack work takes), batches, Desk Recheck, mail and bill scans, backup capture, pack installs and Hermios sign-in, plus nine forms. The cause was a hand-kept list in `serviceBusy()`; each new kind of work had to be added to it by hand.

- **Server:** `server/work-ledger.ts` is one process-wide ledger.
  - Work a restart would cut registers itself where it starts, as "working" or "waiting on the person". Work that is saved and resumes after a restart doesn't register.
  - The shared entry points register for everything that runs through them: job runs, scheduled loops, workspace operations, and the bank import and REI hosts. A workflow pack's work is counted without code of its own.
  - `/api/health` reads only the ledger: `busy` means anything working, and `waitingApprovals` is the waiting count. Both are counts only.
- **Window:** every form that holds typed text uses `useUnsavedGuard(dirty)` from `src/lib/unsaved-work.ts`. It is the same answer `beforeunload` and the update use.
- **Not moved:** the private backup's own idle check (`assertPrivateBackupIdle`) keeps its reason codes for now.

## Edge paths
| Case | What happens |
|---|---|
| Unsaved work when "Restart now" is clicked | Main asks the window first. The card says "Save or discard your open draft first", and the installer never starts. |
| Window doesn't answer within 2 s | The automatic restart waits. "Restart now" goes ahead, because the person chose it. |
| A draft opened while the service stops (up to 15 s) | The window is asked again just before the installer, for "Restart now" too. A draft stops it and the office service starts again. |
| The window shows RealBud's own error or waiting page | That page holds no drafts, so the automatic restart can go ahead. A PC whose office service can't start still gets the fix. |
| Bud's turn waits on an approval card | Counted as waiting on the person, not as Bud working: the automatic restart waits for the answer, and "Restart now" can go ahead. |
| Office service busy | Waits and retries by itself. The card names what it is waiting for. |
| "Restart now" while busy | Retries every 30 s for 10 minutes, then hands over to the safe-moment wait (away or locked). |
| Typing, a new draft, "Not now" or "Later" while the service is stopping | The automatic restart stops, the office service starts again, and RealBud waits for the next safe moment. |
| A newer version arrives while the service is stopping | Same as above; the newer download is installed at the next safe moment. |
| The install marker can't be saved | The automatic restart doesn't go ahead, so a failed install can't repeat unseen. "Restart now" still works. |
| Service can't be stopped | Today's two tries, then "Stop it in Settings & help". |
| A newer version is published while one waits | The hourly check continues and the newest download replaces the older one. |
| Offline or download fails | Retries silently on the next hourly check; a check the person asked for shows the error. |
| Install fails (old version reopens, or the installer never starts) | "0.1.51 didn’t install" with "Try again" and "Download from realbud.app". The automatic restart doesn't retry that version, so the office service isn't stopped every hour; a newer version clears it. |
| Laptop asleep or PC off | Checked again after wake. A download that was cut off resumes on the next check. |
| Dev or unpackaged build | No updater, as today. |

## State kept on disk
`<userData>/update-schedule.json`, written by main only:
- `version`: the update waiting;
- `downloadedAt`;
- `laterUntil`;
- `attemptedAt`, `fromVersion`: written just before an install;
- `installFailed`: the version whose install didn't land.

On load, `laterUntil` is capped at 4 hours ahead and `downloadedAt` at now. A newer download keeps the earliest `downloadedAt`, so a run of releases doesn't restart the 24-hour clock.

On launch:
- If `version` equals the running version and `fromVersion` is set, show "Updated from X". The file is then cleared.
- If `attemptedAt` is set and the running version is still `fromVersion`, show "didn't install".

## Interface between main and renderer
`UpdaterState` keeps today's fields (`status`, `version`, `percent`, `message`, `deferred`) and adds:

```ts
restart?: {
  mode: "when-away" | "countdown" | "waiting";   // waiting = blocked by unsaved work, busy, or an approval
  at?: number;                                   // countdown end, epoch ms
  blockedBy?: Array<"unsaved" | "busy" | "approval">;
  laterUntil?: number;                           // epoch ms; absent when not held
  required: boolean;
  requiredReason?: "unsupported" | "waited";
};
installFailed?: { version: string };
updatedFrom?: { from: string; to: string };
```

New IPC handlers on the office-window guard:
- `update:later` holds the automatic restart; it is refused while required.
- `update:cancel-countdown` is the countdown's "Not now".
- `update:dismiss-note` clears `updatedFrom` or `installFailed`.

Main asks the renderer: it sends `update:query-unsaved` with an id. The renderer answers `update:unsaved-reply(id, { unsaved: boolean })`.

## Out of scope
- Rolling back a bad version.
- Staged rollouts.
- Mac signing.
- A realbud.app-enforced minimum version (the website repo and a deploy).
