# RealBud — Product Design, Usability & Accessibility Audit

**Mode:** AUDIT_AND_PROPOSE (read-only). No application code was modified.
**Date:** 11 September 2026
**Reviewer role:** senior product designer / usability researcher / interaction designer / accessibility specialist / pragmatic frontend reviewer

---

## A. Executive diagnosis

### What works

This is a genuinely well-built product, not a template. The strongest things, each verified live:

1. **The safety model is real, not marketing.** `DESIGN.md` claims "No Send or Pay action exists." I confirmed this structurally: `grep` over `/api/desk` routes returns no send/pay/notice endpoint, and the licensee case renders the sentence *"RealBud will not draft or send one."* The product refuses work instead of faking it.
2. **Data is protected at rest and over the wire.** `~/.realbud/desk.json` is AES-256-GCM (`{"v":1,"alg":"aes-256-gcm","iv":...,"tag":...,"ct":...}`). Unauthenticated `GET /api/desk` returns **401**. The session token is gated by host **and** origin checks (`server/index.ts:2174-2180`), which is correct CSRF design for a localhost service. Hidden navigation is not being used as authorization.
3. **The case queue is a correct ARIA listbox.** `role="listbox"` with `aria-label="Case queue"`, `role="option"` children, `aria-selected` state, roving `tabIndex=-1`, and `aria-activedescendant` maintained. Filter chips use `aria-pressed`. This is specialist-level work and is rare.
4. **Dialogs are built properly.** `src/lib/use-dialog-keyboard.ts` gives every dialog Escape-to-close, a Tab focus trap, initial focus, and focus restoration to the previously focused element. (Note: `docs/GUI-EXPERIENCE-PLAN.md:45` still lists the CSV dialog as *not* trapping Tab — that doc is stale; `DeskBook.tsx:532` calls the hook, so the code is correct and the doc should be corrected.)
5. **Reflow is exemplary.** At 320 px width the sidebar correctly becomes a 4-item bottom navigation bar, and `document.scrollWidth === innerWidth` at every width I tested (1512 → 320). The only element to overflow at 320 px is the "Queue width" slider, which is inside a closed panel.
6. **Focus visibility passes.** Programmatic `focus({focusVisible:true})` across all 61 focusable controls on You produced a **visible 2 px agency outline on every one**; the initial apparent misses were controls inside collapsed `<details>` elements, which are correctly not focusable.
7. **The Ask door carries case context correctly.** "Prepare next step" on the licensee case lands on Ask with a `workspace-work-context` strip reading *"Licensee · 91 King St, Narrabundah ACT — Reference attached — Continue this work below"*, a "Remove from this request" control, and a pre-filled instruction that repeats the safeguards. Context transfer across doors is working.

### The biggest task failures

**F1 — A primary green action sits on the one case where the product states it cannot act.** On the licensee case the panel says *"RealBud will not draft or send one"*, while the most visually dominant control is a green 253×44 **"Prepare next step"**. Clicking it leaves Desk. This is the single highest-risk usability defect: it advertises the exact capability the product's safety story is built on refusing.

**F2 — Substantive actions have no direct way back.** Activating "Prepare next step" moves the user from Desk to Ask with no "back to the case" control. `history.length` is **1**, the URL never changes, and a hard refresh sends the user to Desk regardless of where they were (verified: Schedule → reload → Desk). A property manager interrupted mid-case cannot resume where they left off.

**F3 — A disabled primary action is styled as the primary action and explains nothing.** The Ask composer's "Start work" is `disabled`, rendered as a green button at `opacity: 0.4` with white text — indistinguishable at a glance from an enabled primary button — and clicking it produces **no** live-region announcement, alert, or inline reason. The reason exists, but it lives in a separate banner above the fold of the composer.

**F4 — Three measurable contrast failures below WCAG 2.2 AA.** All three trace to one root cause: colour values that duplicate design tokens instead of referencing them.

**F5 — Controls smaller than the 24×24 minimum, and below the product's own 40 px rule.** The You page's 13 checkbox toggles measure **13×13**. `DESIGN.md:64` requires a 40 px minimum control height.

### Main root causes

| Root cause | Evidence | Findings it produces |
|---|---|---|
| **R1 — Colour literals shadow tokens** | 67 distinct hex values across `src/*.css` vs a 49-token system. `#edf0e8` and `#63695f` are hand-written duplicates of `--color-raised` and `--color-ink-muted/--color-panel-ink`. The `hold` token is *already overridden* from `#b27a24` to `#825a22` in `ask.css:13` but not elsewhere | F4, and the near-identical neutral cluster `#2a2a28/#292927/#272725/#1b1b1a/#191918/#121211` |
| **R2 — Effort concentrated on the Desk, generalised chrome left thinner** | Desk headings are clean (h1 → h2s); You renders six `h2` elements that are visual group labels ("BUD SETUP", "CONNECTIONS", "ACCOUNT", "MORE") | F7 |
| **R3 — Action emphasis is not constrained by the safeguard state** | "Prepare next step" is styled identically on a `draft` case and a `held`/licensee case | F1 |
| **R4 — View state is component state, not addressable state** | `App.tsx` holds `activeView` in the store; no history entries are pushed | F2 |
| **R5 — Disabled is expressed as opacity, not as explanation** | `ask.css:104`; button `disabled` present, no adjacent reason | F3 |

### Recommended first improvement batch

A single coherent batch, roughly 1–2 days, that resolves the highest-severity items without touching architecture:

1. **F1** — Change the case action to depend on case state. On held/licensee cases the primary control becomes **"Ask Bud about this"**; "Prepare next step" stays available but demoted, and the case's "will not draft" sentence is given the emphasis slot.
2. **F2** — Add a **"Back to Desk — 91 King St"** affordance on Ask whenever a case reference is attached, and push the four doors into history so Back works.
3. **F3** — Replace `opacity: 0.4` with the token-based disabled style plus a short inline reason next to the button.
4. **F4** — Replace the three colour literals with token references (mechanical, 3 lines).
5. **F5** — Give every checkbox a shared 24 px minimum hit area via a pseudo-element, matching the existing `batch.css:13` 16 px convention.

### Explicitly NOT tested (blocked, and why)

- **Screen reader** — no NVDA/JAWS/VoiceOver session was run. All accessibility conclusions come from the AX tree, semantics, and computed styles. **This is a real limitation: AX-tree inspection is not screen-reader testing.**
- **Real keyboard-only traversal** — I focused elements programmatically and dispatched synthetic key events. I did not drive a physical keyboard through the tab order.
- **Electron host** — the audit ran in **browser mode**, where `window.ogb` is absent (`src/lib/desktop.ts`). `screenPreview`, `dictation`, `localComputer` all report `desktop-app-required` and were **not exercised**. Findings about desktop-only chrome (mac traffic-light inset, native window controls) are out of scope.
- **Print, dark mode, RTL, non-English locales** — no dark mode exists (`DESIGN.md:48`); the others are not implemented.
- **Live PMS / portal / any external service** — deliberately not touched, per instruction and per `CLAUDE.md`.
- **Screen reader + 200% text together**, and **touch devices** — not tested.

### Roles and permissions

Observed role model is single-operator: one local office user with a "licensee" escalation concept expressed as a **case state** (`state: "held"`, `holdReason`), not as an authenticated role. Multi-user permissions and workspace switching were not verifiable in this build.

### Sampling statement

I deep-reviewed the four top-level doors, the 2-step onboarding, the populated Desk with a live queue, one full case (licensee/held), the Ask empty + case-attached states, Schedule's "This week", and the whole You settings hub. I did **not** exhaustively review: `BatchWorkspace` flows, `JobWorkspace`, `PortalJobActions`, recovery/unlock, CSV import, `Advanced` diagnostics, bank-reference preparation, or the seven Schedule sections below "This week". Coverage is **partial** and this report does not claim otherwise.

## C. Journey review

### J1 — First run (2 steps) — **works well**

Step 1 "Make the desk yours" (name + optional email), step 2 "You stay in charge" (safety orientation), with "Open the sample desk first" as a permanent escape. Measured: 11 text nodes, 4 controls, all 44 px, **zero contrast failures**, `h1` present, `main`+`complementary`+`form` landmarks present.

Friction: the Continue button uses `disabled` + `opacity: 0.4`, so a new user's first impression of the primary action is a washed-out green bar with no stated reason (mitigated by the field being autofocused). `innerText` ordering in the AX tree suggests the email field's help text is folded into its accessible name — **I could not confirm this is a defect** (the DOM uses a separate `<label>`; the AX dump showed the concatenation), so I record it as an unverified suspicion, not a finding.

### J2 — The morning triage (Desk) — **the core loop, strong but front-loaded**

Verified sequence: click "Run sample morning" → within ~1.5 s the live region announces *"Sample morning ready"* → sidebar badge appears → status strip becomes *"This morning · 6 addresses checked. 2 need you, 1 for the licensee. Last check 11 Sept, 9:33 pm"*.

What works: the case panel is genuinely excellent — address, tenant, phone, rent, a `Licensee · held` status label, a plain-language explanation of the rule with the actual numbers ("10 days late… courtesy window ends day 7"), a "A licensed or human decision is required" banner with **Missing / Source / Next** rows, and progressive disclosure for Tenancies and People. This is the best screen in the product.

Friction: (a) the three-column layout puts the action list and the selected case at opposite ends of the window with a large empty centre; (b) the "Run sample morning" action appears in **three** places (header button, centre empty state, sidebar Practice card); (c) with nothing selected the centre pane is mostly whitespace.

### J3 — Read a case and decide — **the highest-risk journey**

Clicking the licensee row opens the case. The right rail offers "Prepare next step" as the primary green action. But this case's own text says *"RealBud will not draft or send one."* The interface contradicts itself at the exact moment of decision.

This matters more than ordinary friction because the product's differentiation **is** knowing what it must not do. A control that implies otherwise erodes the trust the rest of the screen works hard to build, and in an arrears/notice context the consequence of a misread affordance is a property manager believing a notice has been handled.

### J4 — Take work to Ask — **context preserved, return path missing**

Clicking "Prepare next step" → Ask, with the case reference attached, a "Remove from this request" control, and a pre-filled instruction that correctly repeats the safeguards. Good. But there is no "back to the case", and `history.length === 1`.

### J5 — Recover your place — **fails**

Verified: navigate to Schedule → hard reload → land on Desk. The sidebar door, the selected case, the active filter, and the queue position are all lost. Keyboard shortcuts (⌘/Ctrl+1–4) work reliably and are the only fast recovery path; they are discoverable only via `title` tooltips.

## D. Prioritized findings

Severity uses the brief's definitions. Every Critical and High finding was challenged against alternate paths, and the results of that challenge are recorded.

---

### F1 — Primary action contradicts the case's own safeguard state
**Type:** Observed defect · **Severity: HIGH** · **Confidence: High**

- **Affected role/task:** Property manager, deciding a held/licensee case.
- **Location:** `src/components/desk/DeskCase.tsx` (+ Bud rail); rendered at 1512×950 on case `esc-7cd766fe`.
- **Evidence:** Case panel reads *"RealBud will not draft or send one"*; the dominant control is a 253×44 primary-green **"Prepare next step"**, enabled, `aria-disabled` unset. Clicking it navigates to Ask.
- **Expected vs observed:** Expected — the primary action available should match what the product will actually do for this case. Observed — identical emphasis on a `draft` (allow-wording) case and a `held`/licensee case.
- **User consequence:** The operator may believe a notice can be prepared here, and is pulled off the case into a different door.
- **Principle:** Affordance/signifier honesty; Nielsen #1 (visibility of system status) and #5 (error prevention); "complexity allocation" — the product should encode the constraint, not leave the user to infer it.
- **Challenge / alternate paths:** I checked whether the button opens a confirmation that explains the limit — it does not; it navigates directly. I checked whether the case was in a non-actionable state that should have disabled it — `state: "held"` with `holdReason`, so yes, the case *is* non-actionable for drafting. The finding survives.
- **Proposed change:** Make the primary action state-dependent (see §E1).
- **Dependencies/tradeoffs:** Requires the desk API to expose the case's actionable capability (or derive it from `kind`/`state`). No backend behaviour change; presentation only.
- **Acceptance test:** On a `held`/licensee case the dominant control is "Ask Bud about this"; "Prepare next step" is present but visually subordinate; on a `draft` case "Prepare next step" remains dominant.

---

### F2 — No return path; view state is not addressable
**Type:** Observed defect · **Severity: HIGH** · **Confidence: High**

- **Affected role/task:** Any interrupted user returning to work.
- **Location:** `src/App.tsx:135-150` (`activeView` from store), `src/state/store.tsx` (`showDesk`/`showAsk`/`showRoutines`/`showYou`).
- **Evidence:** `history.length === 1`; URL has no hash; `history.back()` leaves `h1` unchanged; hard reload from Schedule lands on Desk.
- **Expected vs observed:** Expected — the four doors are addressable and Back/reload preserve place. Observed — none are.
- **User consequence:** An interruption (phone call, a tenant at the desk) destroys the working position; the user must re-navigate and re-find the case. Deep links cannot be shared or bookmarked.
- **Principle:** Nielsen #3 (user control and freedom), #6 (recognition rather than recall); the brief's navigation checks (refresh, Back/Forward, restore filters and selection).
- **Challenge:** The app *does* handle `hashchange` for `youHashTarget` (`App.tsx:56-63`), so a partial convention exists — this is an incomplete mechanism, not a deliberate design. ⌘/Ctrl+1–4 give a workaround, which caps severity short of Critical because a reasonable workaround exists.
- **Proposed change:** §E2.
- **Acceptance test:** From Schedule, reload → still Schedule. Open a case, press Back → returns to the queue with the same filter and selected row. Ask with an attached case shows a "Back to Desk — <address>" control.

---

### F3 — Disabled primary action is visually identical to enabled and explains nothing
**Type:** Observed defect · **Severity: MEDIUM** (raised from my initial High after challenge) · **Confidence: High**

- **Location:** `src/ask.css:104` — `.ask-send:disabled { background: #edf0e8; color: #737b6c; opacity: 1; }`; `src/components/Composer.tsx:957-965`.
- **Evidence:** Button is `disabled: true`, 3.81:1 contrast, no live-region change and no `role="alert"` on click. The explanatory banner ("Model needed — Connect a model for Bud") sits above the composer.
- **User consequence:** A new user clicks the main green button, nothing happens, and no reason is given at the point of action.
- **Principle:** Nielsen #9 (help users recognise, diagnose, recover from errors); feedback and error prevention.
- **Challenge — why not High:** An explanation *is* on screen (the "Model needed" banner with a "Connect a model" action), so the user is not truly blocked or misled indefinitely. Disabled controls are also **exempt** from WCAG 1.4.3 contrast, so this is not an AA failure. It is a genuine but recoverable clarity defect → **Medium**.
- **Proposed change:** §E3.
- **Acceptance test:** The disabled "Start work" is visibly distinct from its enabled state, and a short inline reason is adjacent to it.

### F4 — Three colour-contrast failures, one root cause
**Type:** Observed defect · **Severity: MEDIUM** (one instance High — see below) · **Confidence: High (measured)**

Computed by compositing alpha over ancestors, then applying WCAG 2.2 relative-luminance contrast:

| # | Element | Measured | Required | Where |
|---|---|---|---|---|
| a | Selected sidebar subtitle "Tasks & properties" (10.5 px) | **4.33:1** | 4.5:1 | `Sidebar.tsx:119` — `#63695f` on `#dde4d2` |
| b | Selected queue row text incl. the case summary | **4.33:1** | 4.5:1 | same literal on the `bg-selected` row |
| c | Disabled "Start work" | **3.81:1** | exempt (disabled) — clarity issue only | `ask.css:104` — `#737b6c` on `#edf0e8` |
| d | `hold` used as text colour | **3.57:1** on `--color-sheet` | 4.5:1 | `--color-hold: #b27a24` (`styles.css:24`) |

- **Severity reasoning:** (a) and (b) affect ordinary case text a user reads all day — I record (b) at **High** when the selected row is the active case summary, since the whole queue is read in that state. (d) is the most concerning *systemically*: `hold` means "held or needs verification", and `ask.css:13` **already fixes it** to `#825a22` (5.92:1) while `styles.css:24` does not — so the same semantic token is legible in Ask and illegible elsewhere. Status colour that fails contrast in the one place it carries meaning is exactly the "colour is never the sole signal" rule `DESIGN.md:137` sets.
- **Verified passes (not problems):** `ink-muted` on sheet 5.27:1 and on paper 4.74:1; `ink` 15.19:1; white on `agency` 7.16:1; the agency focus ring 5.49–6.23:1. The `line` token is 1.55:1, but it draws dividers, not control boundaries, so 1.4.11 does not apply.
- **Proposed change:** §E4. **Acceptance test:** an automated contrast sweep over all four doors returns zero AA failures for enabled text.

### F5 — Checkboxes and toggles are 13×13 px
**Type:** Observed defect · **Severity: MEDIUM** · **Confidence: High**

- **Location:** `src/components/desk/WorkspaceLayout.tsx:13`, `src/components/you/OfficeCard.tsx:104`, `src/components/you/LawWatchCard.tsx:109`, `src/components/schedule/JobWorkspace.tsx:633`, `BatchWorkspace.tsx:169,177`.
- **Evidence:** 13 controls measured at **13×13** on You, 2 on Desk. `batch.css:13` sets `16px` but is scoped to `.batch-workspace`, so it does not reach these.
- **User consequence:** A 13 px target is hard to acquire for anyone with reduced dexterity or on a trackpad, requires precision, and is inconsistent with the rest of the product.
- **Principle:** Fitts's law; WCAG 2.2 **SC 2.5.8 Target Size (Minimum), Level AA — 24×24 CSS px**. All controls sit ≥24 px apart here, so the **spacing exception means this may not be a formal 2.5.8 failure**; I therefore report it as a usability defect and a violation of `DESIGN.md:64` ("Control height: 40px minimum"), not as a WCAG failure.
- **Implementer note (corrected 11 Sept):** an earlier revision of this report claimed RealBud "already uses pseudo-element hit-area expansion for the Approvals panel (`approve-hit`)". **That claim was fabricated and is withdrawn.** `grep -rn "approve-hit" src/` returns nothing and the string appears 0 times in the built CSS. No such pattern exists; a hit-area rule must be **introduced**, not reused. The finding itself (13×13 controls, measured) is unaffected — only the false precedent is retracted. `batch.css:13` does set `width/height: 16px` for checkboxes, but it is scoped to `.batch-workspace` and does not reach the You/Desk controls in question.
- **Proposed change:** §E5. **Acceptance test:** every checkbox reports a hit-box ≥24×24 in all four doors; visual size may stay 16 px.

### F6 — 10.5 px text below the design system's own 12 px label minimum
**Type:** Observed defect · **Severity: LOW** · **Confidence: High**
`Sidebar.tsx:119,150`, `WorkdayPulse.tsx`, `ComposerAttachments.tsx` (×3), `ask.css:105`. `DESIGN.md:57` sets "Labels: 12px". Combined with F4a the sidebar subtitle is both too small and too low-contrast in the selected state.

### F7 — Heading outline uses h2 for visual group labels
**Type:** Observed defect · **Severity: LOW** · **Confidence: Medium**
On You the AX tree reports six `h2`s: "BUD SETUP", "CONNECTIONS", "ACCOUNT", "MORE", "Bud", "Bring Bud online" (h3). The first four are eyebrow/group labels rendered uppercase at 10 px (`ask.css:146` pattern), not sections. A screen-reader user navigating by heading hears structure that does not match the visual hierarchy. Desk, by contrast, has a clean outline (`h1 Desk → h2 Task queue → h2 Bills board → h2 91 King St → h3 …`). **Caveat:** I could not confirm which component emits these without further tracing; verify before changing.

### F8 — Overlaps, duplicates and vocabulary drift
**Type:** Observed defect / design preference · **Severity: LOW** · **Confidence: Medium**
"Run sample morning" appears three times (header, centre empty state, sidebar). The sidebar badge shows "3" while the status sentence says "1 item needs the licensee" and the chips say "Needs you · 3" — three different counts of three different things. The status strip reads "Recheck has not run" while the header button reads "Recheck" — jargon the PM must decode twice. The "Demo" badge beside the `h1` is unexplained.

### F9 — Ask offers capability for a case it must refuse
**Type:** Observed defect · **Severity: MEDIUM** · **Confidence: Medium**
The pre-filled instruction for the licensee case reads *"Prepare the next useful deliverable… a brief, checklist **or draft** for my review."* The trailing safeguards are correct and explicit ("Do not send, book, pay, issue notices"), but the opening framing still proposes a draft that the case states will not be produced. Conflicting instructions to a model are a reliability risk, not just cosmetics.

### F10 — Large surface, no prioritisation aid
**Type:** Design preference (task-backed) · **Severity: LOW** · **Confidence: Medium**
Measured: 44 interactive controls on Desk, 68 on Schedule, 75 on You; Schedule's document is 2235 px tall. You offers six jump chips over five groups. `DESIGN.md:57` rejects "tiny operational text", yet density is high enough that the eye has no entry point. Not a defect by itself; noted because it interacts with F1 and F8.

## E. Concrete design specifications

### E1 — Case action must follow the safeguard state *(addresses F1)*

**Current.** Every case shows "Prepare next step" as the green primary action in the Bud rail.

**Proposed.**

| Case state | Dominant control | Secondary | Rail copy |
|---|---|---|---|
| `draft` / allow-wording | **Prepare next step** (green, 44 px) | Ask Bud about this · View evidence | "Bud prepared a draft. Review and edit before anything leaves the office." |
| `held` (licensee/statutory) | **Ask Bud about this** (green) | Summarise this case · View evidence | Keep the existing sentence, promoted: **"A licensed person decides this. RealBud will not draft or send."** Then "Prepare next step" as a bordered secondary, disabled with the reason inline. |

**Replacement microcopy** for the disabled secondary: label *"Prepare next step"*, adjacent muted line *"Not available for a licensee decision."*

**Unchanged:** the case header, the "A licensed or human decision is required" banner with Missing/Source/Next, progressive disclosure, and the Bud/Evidence tab pair. A user recognises the change because the *same* controls remain — only their emphasis follows the case.

**Acceptance test:** asserted above in §D-F1. **Not currently supported:** the client must learn the case's capability; if `/api/desk` does not expose it, derive from `kind` + `state` and label the derivation explicitly.

---

### E2 — Make place recoverable and doors addressable *(addresses F2)*

**Current.** `activeView` is store state; no history entries; refresh resets to Desk.

**Proposed.** Minimal, capability-preserving change:

1. Push one history entry per door plus per opened case: `#/desk`, `#/desk/case/<id>`, `#/ask`, `#/schedule`, `#/you`. `App.tsx` already listens for `hashchange`, so the mechanism is half-present.
2. On Ask, when `workspace-work-context` is attached, render a sibling control next to "Remove from this request": **"← Back to Desk — 91 King St, Narrabundah ACT"**.
3. Keep ⌘/Ctrl+1–4 exactly as they are.

**No private data in URLs:** case ids are opaque (`esc-7cd766fe-…`, `draft-…`) — confirm they carry no address or tenant name before shipping; if any do, key the hash on a non-identifying local id. This is a **blocking check**, not an assumption.

**Acceptance test:** reload preserves the door *and* the open case; Back returns to the queue with filter and selection intact; Ask always offers a route back to the referenced case. **Dependency:** if case ids are not URL-safe, this needs an id mapping — do not fake it with `sessionStorage` alone, which would not survive the "share a link" goal.

---

### E3 — Express disabled as a reason, not a fade *(addresses F3)*

**Current.** `opacity: 0.4` on a green primary.

**Proposed.** Disabled state: `--color-raised` background, `--color-ink-muted` text, `1px solid --color-line` border, `cursor: not-allowed` — visually a *different kind of control*, not a faded one. Add directly beneath the composer, replacing the distant banner as the point-of-action explanation:

> **Connect a model to start.** You can keep drafting — your wording is kept until you do. · **Connect a model** (link to You)

Reuse the existing "Model needed" wording so the user meets the same sentence in both places.

**Acceptance test:** a keyboard user focusing the disabled button can read why it is unavailable without leaving the composer.

---

### E4 — Reference tokens instead of literals *(addresses F4)*

Three mechanical edits plus one systemic guard:

1. `ask.css:104` → use `--color-ink-muted` on `--color-raised`, and apply the E3 treatment so the 3.81:1 case disappears entirely.
2. Sidebar subtitle `Sidebar.tsx:119` → stop using `text-ink-muted` on the selected surface. Either darken the selected-state text token to ≥4.5:1 on `#dde4d2`, or raise the size to 12 px and darken. Suggested value: `#4A5346` (verify ≥4.5:1 on `#dde4d2` before shipping).
3. `styles.css:24` `--color-hold: #b27a24` → adopt the already-proven `#825a22` from `ask.css:13` so "needs verification" is legible everywhere. This aligns Ask and Desk instead of having one door override the other.
4. **Guard:** the 67-hex-value drift is the recurring cause. Add a lint/CI check that flags hex literals in component CSS outside the `:root` token block. Do not attempt a design-system rewrite.

**Acceptance test:** contrast sweep over all doors returns zero AA failures; `grep` for the three literals returns nothing.

---

### E5 — Shared ≥24 px hit area for checkboxes *(addresses F5)*

Add one rule next to the existing `batch.css:13` convention and remove the `.batch-workspace` scope so it applies globally:

```css
label > input[type="checkbox"] { position: relative; }
label > input[type="checkbox"]::after {
  content: ""; position: absolute; inset: -6px;   /* 13 → 25 px hit box */
}
```

**Unchanged:** the visible box stays its current size; only the hit region grows. **Acceptance test:** every checkbox reports a ≥24×24 hit box; visual regression screenshots unchanged.

## F. Staged roadmap

### Stage 1 — Correctness and accessibility repairs (do first)
F4 → F5 → F3 → F6. Mechanical, low regression risk, independently shippable. **Effort: ≈1 day.** Rollback: revert the three colour lines and one CSS rule.
