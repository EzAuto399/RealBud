# Stock Hermes, multiple instances and CrossDesk

Research snapshot: 13 September 2026. Scope: **Kevin first; a second staff member is deferred.** This document records upstream capabilities and their relationship to RealBud. It does not activate another operator, remote access, accounts or a gateway. Runtime admission was tested separately; the latest receipts below distinguish candidate proof from installed-app activation.

## Decision

Keep Bud as RealBud's supervised product layer above unmodified Hermes. Reuse stock profiles, sessions, learning and supported transport interfaces. Hermes already supports multiple instances and connections across machines. Those facilities do not require replacing RealBud with Hermes Desktop or creating an engine fork.

“Cross desk” has two plausible meanings. Hermes documents connections to different agent backends. **CrossDesk** is also a separate remote-desktop project maintained under the GitHub account `kunkundi`. No official Hermes–CrossDesk integration was found in the official documentation and targeted source review. Treat a CrossDesk integration as proposed work, not a shipped Hermes feature.

For Kevin, these capabilities are useful for isolated testing and an optional named execution machine. They do not change the immediate scope: four preparation stages— inbox triage, invoice intake, expected-bill review and ANZ reference preparation—supporting the two commercial outcomes of bill handling and rent-reference work. The product must preserve source evidence, human decisions and one RealBud office clock.

## What “multiple instances” actually gives us

| Capability | Stock Hermes evidence | RealBud implication |
|---|---|---|
| Multiple conversations | Sessions carry conversation history. | Useful primitive; a conversation is not an account or filesystem permission boundary. |
| Multiple profiles | Each has its own configuration, memories, skills and session database. | Preserve Kevin's native learning outside versioned runtimes. Use a separate disposable profile for candidate testing. |
| Multiple profile gateways | Separate gateways are supported. An optional multiplex mode serves several profiles in one gateway. | Available upstream; no need to activate it for Kevin's initial build. It is not a reason to introduce another office scheduler. |
| Connections across machines | Hermes Desktop registers local, remote, SSH and cloud backends. The selected backend owns execution. | A supported backend concept we can adapt; this Desktop UI is not present automatically in RealBud. |
| Work between backends | Delegation stays gateway-local by default. Crossing backend boundaries needs an explicit bridge. | Name and authenticate the executing machine; do not silently treat its files, accounts and tools as local. |

Sources: [sessions](https://hermes-agent.nousresearch.com/docs/user-guide/sessions), [immutable profile documentation](https://github.com/NousResearch/hermes-agent/blob/939e45c91d751fadd94dcd1b873ac3cb44846213/website/docs/user-guide/profiles.md#L9), [immutable multi-profile gateways](https://github.com/NousResearch/hermes-agent/blob/939e45c91d751fadd94dcd1b873ac3cb44846213/website/docs/user-guide/multi-profile-gateways.md#L61), [immutable multi-connection documentation](https://github.com/NousResearch/hermes-agent/blob/939e45c91d751fadd94dcd1b873ac3cb44846213/website/docs/user-guide/multi-connection-desktop.md#L272). Multi-connection and multiplex gateway documentation already exists in the compared 0.21.0 source; these are not capabilities first introduced by 0.21.2. [0.21.0 connection types](https://github.com/NousResearch/hermes-agent/blob/29112bef099274229cadff79cdff7bf7b99c4b77/apps/desktop/electron/connection-registry.ts#L47), [0.21.0 gateway configuration](https://github.com/NousResearch/hermes-agent/blob/29112bef099274229cadff79cdff7bf7b99c4b77/gateway/config.py#L980).

Two constraints matter even with one human operator:

- Upstream warns against two independent agent processes writing the same profile. Profiles isolate Hermes state, not the OS account's filesystem. External tools retain the real OS `HOME` by default. A different chat or profile alone does not separate all credentials. [Profile process and filesystem boundaries](https://github.com/NousResearch/hermes-agent/blob/939e45c91d751fadd94dcd1b873ac3cb44846213/website/docs/user-guide/profiles.md#L13).
- `max_concurrent_sessions` is a capacity control whose local registry can fail open. It is neither a security boundary nor a desktop ownership lock, and it is not designed for a shared Hermes home mounted across machines. [Concurrency contract](https://github.com/NousResearch/hermes-agent/blob/939e45c91d751fadd94dcd1b873ac3cb44846213/website/docs/user-guide/configuration.md#L2356).

RealBud should therefore coordinate overlapping Ask/Prepare work deliberately. Its existing computer lease is explicitly in-process, and expiration alone does not establish that an old controller stopped. Those constraints remain even if the engine accepts concurrent conversations. [Lease implementation](../server/computer-lease.ts:1).

## Native computer tools are separate from remote backend connections

Latest Hermes documents a native computer wrapper using a Cua driver over MCP. The released documentation expects the **Cua 0.20 contract**. macOS permissions still apply, and Windows started through SSH has an additional interactive-session requirement. [Latest computer-use contract](https://github.com/NousResearch/hermes-agent/blob/939e45c91d751fadd94dcd1b873ac3cb44846213/website/docs/user-guide/features/computer-use.md#L65), [official Cua Windows SSH guide](https://cua.ai/docs/how-to-guides/driver/windows-ssh).

RealBud currently declares `@trycua/cua-driver` **0.19.3** and explicitly mounts computer MCP descriptors in its ACP adapter. Latest Hermes' native ACP bundle excludes its `computer_use` wrapper. Consequently, a stock runtime update or a profile toggle does not by itself migrate RealBud to that wrapper or prove remote computer operation. Test an explicit supported adapter path and driver version together. [RealBud driver dependency](../package.json:68), [explicit computer mount](../server/drivers/acp/core.ts:215), [latest native toolsets](https://github.com/NousResearch/hermes-agent/blob/939e45c91d751fadd94dcd1b873ac3cb44846213/toolsets.py#L69), [latest ACP session tool selection](https://github.com/NousResearch/hermes-agent/blob/939e45c91d751fadd94dcd1b873ac3cb44846213/acp_adapter/session.py#L393).

A Mac-hosted agent can work on its authorized websites and files. Working inside a Windows-only application still requires an actual Windows execution environment. Connecting to an agent on a Mac, viewing a Windows desktop and granting a tested Windows automation adapter are three distinct arrangements; none establishes the other two.

CrossDesk documents direct peer connections with TURN fallback, WSS signaling and an SRTP option required for its web controller. It supports keyboard/mouse, clipboard and files; its Windows service can handle protected desktop states. A remote machine must have the host installed, running and connected. These are vendor capabilities, not tests performed here. [Pinned desktop documentation](https://github.com/kunkundi/crossdesk/blob/58225de7ea463c3b08598fe98400dc648b276b1e/README_EN.md#L48), [pinned server architecture](https://github.com/kunkundi/crossdesk-server/blob/858afc9f70f19565f280e79de69189c41ec87d9f/README_EN.md#L1).

Its privacy document distinguishes the public signaling/relay service from self-hosting and says startup version checks still occur with self-hosting. Session content can include screens, audio, input, clipboard and transferred files. Selecting a remote-control product therefore selects a data path as well as a screen viewer. This is not an independent security assessment or a guarantee of encryption in every configuration. [Pinned privacy description](https://github.com/kunkundi/crossdesk/blob/58225de7ea463c3b08598fe98400dc648b276b1e/PRIVACY.md#L61).

No documented Hermes adapter or MCP control interface was found in the reviewed CrossDesk repositories. The server's administrative interfaces are not evidence of an agent control protocol. CrossDesk could be evaluated separately for Kevin's human access or takeover. Bundling it or using it as Bud's control transport needs an explicit interface, ownership rules, observable Stop/reconnect behavior and review of the licences for the exact components distributed. It is not needed merely to retain RealBud above stock Hermes.

## Approval admission remains a separate gate

The current RealBud adapter uses supported safe mode to suppress configured MCP/plugins/hooks/webhooks while preserving native learning and explicitly mounted tools. Its random `--toolsets` argument does **not** remove every native ACP tool: the latest ACP session still constructs `hermes-acp`, including `execute_code`. [RealBud environment contract](../server/drivers/acp/hermes.ts:13), [latest toolset declaration](https://github.com/NousResearch/hermes-agent/blob/939e45c91d751fadd94dcd1b873ac3cb44846213/toolsets.py#L187).

Latest source still approves whole scripts automatically when the context is neither gateway nor ask; direct Python subprocess calls can bypass terminal-string checks. ACP marks its context interactive. This is a source-confirmed approval-path discrepancy, not proof of a live exploit. RealBud now forces the supported `HERMES_EXEC_ASK=1` route. Separate real-model ACP receipts show permission before effects, denial without effects, one-shot narrowing, a second script asking again in the same session, and disconnect without effects. A stock-tool no-callback check also blocked. These close the observed adapter approval-path discrepancy on the tested candidate, without making native Python an OS sandbox. This reviewer read the receipts; the runtime agent performed those tests. [Actual ACP receipts](../outputs/realbud-hermes-latest-2026-09-13/execute-code-approval.json), [no-callback receipt](../outputs/realbud-hermes-latest-2026-09-13/no-approval-callback.json). No upstream source was patched. [Latest script guard](https://github.com/NousResearch/hermes-agent/blob/939e45c91d751fadd94dcd1b873ac3cb44846213/tools/approval.py#L1063), [ACP callback setup](https://github.com/NousResearch/hermes-agent/blob/939e45c91d751fadd94dcd1b873ac3cb44846213/acp_adapter/server.py#L741), [earlier RealBud finding](REALBUD-HERMES-CAPABILITY-REVIEW-2026-09-13.md#a-material-ask-capabilityapproval-discrepancy).

## Small rollout boundary

| Use upstream now through an admitted integration | Evaluate only if Kevin needs it | Still requires RealBud work and proof |
|---|---|---|
| Unmodified runtime, native memory/skills, supported ACP and explicitly mounted tools | A named remote execution machine; CrossDesk for human access | Device identity and ownership, action-bound approvals, Stop/recovery, source/result validation and durable job receipts |
| Separate disposable candidate profile and immutable runtime selection | Native computer wrapper with its matching driver contract | Compatibility tests through RealBud's actual adapter and installed app |
| Kevin's four preparation stages and existing approved data sources | Additional upstream skills suited to those stages | Coverage, dedupe, correction persistence, due runs and blocked-work visibility |

The immediate acceptance evidence is: model/file/native-learning/restart tests on the admitted runtime; configured-versus-explicit MCP isolation; a denied whole-script action that leaves no artifact; simultaneous Ask/Prepare behavior without uncontrolled shared-profile writers; one device controller with Stop and recovery; and all four preparation stages returning honest complete/partial/blocked results. For a remote machine, add authenticated machine routing and receipts identifying where files and actions occurred. For a Windows application, add tests on that Windows machine in its actual login/permission state. These are proof gates, not completed tests in this research.

Maintain no-send, no trust-money mutation and no statutory drafting boundaries. RealBud keeps the office clock and product decisions. Hermes remains the independently updatable engine. The deferred staff architecture remains a separate later decision, not a dependency of Kevin's proposal.
