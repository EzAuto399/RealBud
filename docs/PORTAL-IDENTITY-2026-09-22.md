# Stable portal identity — 22 September 2026

This is the identity prerequisite for [enrolled remote approval](../outputs/skill-history-2026-09-22/remote-approval-next-plan.md). It does not enable enrollment, upload private previews, grant workspace access or launch work. The overall RealBud goal remains active.

## Behavior and boundaries

A new successful sign-in retains the verified Supabase user ID and configured provider origin, a stable portal-person UUID, the provisioned account ID, company ID and account identity epoch. The signed version-2 cookie also contains authenticated time and an expiry of at most seven days. Exact schemas, bounded values, expiry and signature verification prevent a malformed version-2 cookie from falling back to the old email-only format.

The first binding uses a server-verified, confirmed email to locate exactly one explicitly provisioned account. It commits the provider identity once. Duplicate normalized email rows, a different provider identity claiming an already-bound account, or a previously bound provider following a recycled email cannot silently remap that identity. This first binding grants no workspace capability; attended enrollment is still required later.

Database triggers advance the identity epoch on email, company, role or disabled-state changes, including changes back to an earlier value. Subject/account-key/epoch overrides are rejected. Deleting and recreating an account produces a new incarnation; immutable provider bindings and minimal subject records remain, so the old binding cannot revive. Replacement people require deliberate provisioning and fresh workspace enrollment, not reassignment of an existing person's provider binding.

`requirePortalPerson` checks the current authoritative identity on every call. Version-2 billing and operator gates use that same check. All seven directly updated account pages, the existing AI billing account gate, the admin layout and each of the three admin pages use the gate rather than resolving an old version-2 cookie by email. The identity status endpoint returns only the current email/agency label and a statement that workspace permission requires separate enrollment; it exposes no provider subject, internal binding or permission token. The Computers page shows verified versus legacy sign-in and explains how to verify again. Unavailable or changed identities show bounded recovery messages.

Existing legacy cookies retain their pre-existing billing and protocol-1 request behavior. They cannot enter the new person gate. The only newly minted legacy login is an explicitly allowlisted, unprovisioned operator after verified provider sign-in; conflict, disabled identity, missing migration or backend failure never produce that fallback. This is not a claim that every legacy portal operation has been converted to immutable-person authorization.

The callback now separates the SDK client used to verify an OTP from the administrative client used for the protected identity RPC. The installed Supabase SDK saves a successful OTP user's session in per-client memory even with `persistSession:false`; reusing that client caused the RPC to carry user authority rather than the service role. Actual built-site evidence reproduced this failure. A fresh administrative client fixes it without relaxing SQL permissions. Failed callbacks clear any earlier cookie, and accept only supported OTP types, a valid verified provider UUID and a confirmed email timestamp.

## Persistence and operation

The migration is `website/supabase/migrations/202609220002_portal_people.sql`. Apply it after the existing billing schema and before deploying the new callback. This checkpoint did not apply it to a hosted database. Missing migration/backend fails closed for new bound sign-ins. The existing billing rows and their account data are preserved; historical identity records must not be dropped as an ordinary rollback or reprovisioning shortcut.

The two callable RPCs are `realbud_portal_person_login` and `realbud_require_portal_person`. They are service-role-only security-definer functions with a fixed search path. Anonymous/authenticated roles cannot call them or read/write the identity tables; the service role cannot mutate the identity records directly. Inputs and returned documents match TypeScript bounds, including Unicode boundary whitespace and UTF-16 lengths. Invalid first-bind output cannot leave a committed unusable binding.

Short identity transactions serialize account mutations and binding checks with one documented advisory lock acquired before billing row locks. Supported RPC isolation is READ COMMITTED. Higher-isolation snapshots are explicitly rejected because an old snapshot could otherwise outlive a concurrent revocation. No-op provisioning upserts do not create spare permanent identities. This is correctness evidence, not a multi-agency throughput benchmark.

A standalone identity assertion does **not** atomically authorize a later effect. Remote enrollment, preview disclosure, decisions and execution claims must repeat the exact subject/provider/account/company/epoch check inside the same authoritative transaction as their state change, with compatible lock order. Existing protocol-1 requests are unchanged; new remote-authorized requests must use their separate versioned contract and cannot fall back to the legacy claim path.
