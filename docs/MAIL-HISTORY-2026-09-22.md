# Windowed, checkpointed Gmail history acquisition

Status: local source implementation verified on 22 September 2026 against the fictional connector only. No live Gmail account, no managed-service provisioning, no packaged or Windows evidence. Austin workflow 2 step 1 ("bounded historical interval … pagination … a completion/checkpoint receipt. An incomplete scan must say what was not checked").

## What was built

A historical acquisition path beside the existing single-window `collect()`, not replacing it.

**Plan (`shared/mail-ingestion.ts`).** `planMailHistory()` divides the agency-approved interval into fixed windows and `mailHistoryWindows()` recomputes the boundaries from the plan, so the plan stays the only source of truth for what the interval was and how it was divided. Windows are newest-first and tile the interval with no overlap and no gap: `windows[i].startAt === windows[i+1].endAt`, `windows[0].endAt === approvedEndAt`, `windows.at(-1).startAt === approvedStartAt`. Interior boundaries are office-calendar day starts (`officeDayStart`/`officeDayOrdinal`), counted as dates rather than 24-hour durations, so a DST transition inside the interval cannot move or drop a day. Bounds: 1–90 total days, 1–30 window days, ≤ 16 windows, 1–500 messages per window, `maxMessagesTotal = windowCount × maxMessagesPerWindow`.

**Checkpoint (`server/mail-ingestion.ts`).** `collectHistory(purpose)` persists the checkpoint through the existing private-storage helpers (`privateDirectory` / `writePrivateJson` / `readPrivateJson`, temp → fsync → rename at 0600) at `<workroom>/mail-history/checkpoint.json`, validated by `parseMailHistoryCheckpoint()` on every read and before every replacement, so a damaged file fails closed as "needs recovery" and is preserved. The next window's intent (`status: 'running'`, `attemptedAt`) is written **before** the provider is asked for it; on restart an unconfirmed window is visibly not-checked and is read again, while a window already `complete` is never requested a second time. Each window re-verifies account, binding and settings revision after the provider await and settles that window honestly before failing. Per-scan caps become per-window caps (`maxMessages` per window, further reduced by the remaining plan allowance), and the plan total bounds the whole run.

**Idempotency.** The checkpoint stores source identity only — `hash([workspaceId, accountId, threadId, messageId])`, timestamp, direction and a message digest. No bodies, subjects, sender addresses or attachment metadata are copied into it. Replaying the same messages replaces the same keyed rows, so a repeat run adds zero records.

**Coverage receipt.** `mailHistoryCoverage()` derives the completion receipt from the checkpoint alone — no second source of truth: `checkedFromAt`/`checkedToAt`, windows complete / partial / failed / not-checked, `windowsWithUnfetchedPages`, `messagesSeen`, deduplicated provider `gaps`, and plain `notChecked` sentences naming each unchecked date range in the office timezone (plus one for a reached total cap). `historyCoverage()` reads it without collecting.

No schedule activation, no sending, no attachment contents, no provider keys. Credential-shaped input is still rejected by the unchanged validators.

## Limits and what is not proved

- **Fictional connector only.** No live Gmail OAuth, no real pagination behaviour, no real mailbox mutation during pagination. The existing `scanGmailReadOnly` adapter is unchanged and still does its own internal listing pagination (≤ 20 pages, ≤ 100 threads) inside one window; `collectHistory` composes windows on top of that seam and did not gain a provider page cursor of its own.
- **90 days remains the approved ceiling.** `validateAgencySettings` and the setup UI bound `mailScope.historyDays` to 1–90, so the widest plan today is three 30-day windows. Full-year recurrence needs that approved interval widened in `server/agency-setup.ts` and `src/components/schedule/AgencyWorkflowSetup.tsx`, which this packet did not own. Seven days still yields one window; 90 days now yields three checkpointed windows, which is what changed.
- **No HTTP route.** `collectHistory` and `historyCoverage` are service methods only. `server/index.ts` and `server/session-auth.ts` were not touched, so nothing exposes the history coverage to the UI yet and no UI shows "history checked from X to Y". The QA check therefore drives the service seam in process rather than through `/api`.
- **No bill records.** History acquisition produces coverage and source identities; it does not create `mail-item`, `mail-source` or bill occurrence records. `validateMailSource` requires a stored source window to equal `historyDays × 86 400 000`, so per-window bundles deliberately do not enter the encrypted workflow graph. Recurrence detection, the expected-bills register transaction and calendar projection are still open.
- **Single-process fencing.** The in-process acquisition guard serialises `collectHistory` against `collect()`. There is no cross-process owner fence for history as there is for DB scans; two services on one workspace could both collect, and the last atomic write wins.
- No packaged, Electron, Windows, backup/restore or browser evidence for this path. Backup does not carry the history checkpoint file.

## Continuation: collection starts from the verified connection, not a manual action

Status: local source implementation verified on 22 September 2026 against the fictional connector and in-process seams only. The app server is **not** wired yet — the host wiring is delivered as `outputs/mail-history-2026-09-22/index-patch.diff` and is unapplied, so nothing in a running RealBud starts history collection until that patch lands. No live Gmail, no packaged, Electron, Windows or backup/restore evidence.

**Trigger.** `createAgencySetupService` gained an injected `onGmailVerified({ accountId, settingsRevision, historyDays })`. It fires only when the *projected* `gmail` check is `passed` — the same condition that lets a reviewer approve the source — after `POST /api/agency-setup/check-gmail`, and again from the review that first records an approval (verification and review land in either order at first-time setup, and without the second offer a first run would hold until the next Gmail check). A hook failure is caught: acquisition is evidence, never authority, and it can neither pass nor fail a setup check. There is no "collect history" action.

**Once per approval.** `startHistory` in `server/mail-ingestion.ts` keys the run on `(accountId, settingsRevision)`. A repeat check joins the run in flight (it returns the same promise) and never restarts a completed one; a changed approval plans again, and the superseded checkpoint is copied to `<workroom>/mail-history/previous.json` before the new plan is written, so coverage already proved is retained rather than overwritten away. `resumeHistoryIfPending()` continues a checkpoint with unconfirmed windows at service start and reads nothing when none is pending. Every window still re-verifies account, binding and settings revision after the provider await, so a withdrawn connection settles that window honestly and holds with the checkpoint intact.

**State.** `mailHistoryStatusDetail` / `mailHistorySetupDetail` (`shared/mail-ingestion.ts`) are the one wording. The mail-workspace read model carries `history` (`History: checking N of M windows.` / `History: complete (M of M windows).` / `History: held (reason).`) through the service's `get()`, and the setup `gmail` check appends the same facts as a sentence that never claims a complete mailbox. Held reasons from an adapter pass `redactSecretsInText` and are bounded; anything unexpected becomes a plain sentence.

### Added limits

- **No host wiring in the app.** Until the patch is applied, `startHistory`, `resumeHistoryIfPending` and `historyStatus` have no caller in `server/index.ts`, so no HTTP surface starts, resumes or displays history.
- **Single-process, in-memory run state.** The run record lives in the service instance; the durable truth is the checkpoint. Two services on one workspace still have no cross-process fence for history, and `previous.json` keeps exactly one superseded checkpoint.
- **Nothing downstream.** Collection still produces coverage and source identities only — no bill records, no recurrence detection, no schedule activation and no attachment contents.
