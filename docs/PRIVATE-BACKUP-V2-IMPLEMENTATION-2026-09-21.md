## Implemented

- Authenticated framed archives and encrypted logical catalogs, full footer/EOF and business-graph checks. V2 omits the source installation key. V1 readers keep their existing format and limits.
- Durable sliced upload receipts, prefix resumption, artifact rehash, process ownership, interrupted-write fsync and cancelled-only retention. The sliced browser helper is not connected to HTTP/UI yet.
- Bounded source capture, exact ordinary bytes, fixed SQL schema/insertion ordering and second source/authority verification. The caller must hold a real host write lease; capture tests supply fixture leases.
- Logical restore resets Desk/handoff authority, source-account selection and setup reviews, pauses plans/clocks, interrupts mail/execution and rebuilds execution hash bindings. Drafts and permanent retry identities remain retained. Representative tests compare actual v1 restore results.
- Prepared artifacts keep final randomized destination ciphertext exactly, encrypted under the unchanged destination key. Authenticated before/intended hashes and ordered chunks support immutable sealing and restart replay.
- Compact cold restore validates all prepared data before mutation, accepts only before/intended target states during recovery, rejects changed settings/membership and unfinished database sidecars, and preserves evidence on failure. A process-owned SQLite lock prevents concurrent v2 stage/apply writers. Replacements authenticate and fsync before rename; temporary files stay outside the guarded company directory on the same filesystem.
- Actual `server/bootstrap.ts` handles v1/v2 before application stores load, rejecting conflicting stages. Legacy export/stage refuses pending v2 staging. Completed v2 restoration uses the existing validated status receipt.
- The host now has a queue-preserving snapshot lease, integrated first into the existing v1 export route. It stops clock admission, drains admitted background work, blocks business HTTP requests and holds new Telegram/Discord/Slack work without calling their queue-clearing stop methods. Health/status/service recovery remain available. Queue pressure or a deadline cancels the snapshot and releases waiting work; an independent execution-time check retains newer restore/shutdown holds. Remote decisions recheck the current paired account and review fingerprint after waiting. The v2 capture/coordinator still needs this lease wired through its public operation path.
- Automatic portfolio batch recovery checks reversible host admission both before and after its asynchronous connection probe. A snapshot/restore/shutdown hold preserves the paused batch, its bytes and attempt counts; a later permitted probe resumes it. The terminal batch `stop()` is not used for a temporary snapshot. Existing model turns/running jobs cause quiet-workspace backup admission to refuse before capture; handler drain is not a promise to wait for an entire model turn.

- Portfolio `work-batches.json` now participates in v1 and v2 source discovery/validation and authority-reset restore. Exact inner sources, results, request identities, attempt counts and review timestamps survive. Automatic continuation/wait flags and retry timers are cleared; running work becomes interrupted; queued work requires an explicit resume. The production batch reader uses the same extracted legacy-compatible validator. Oversized/malformed history fails the whole backup, and a recovery transform that exceeds the final file limit is refused before staging. This does not remove the existing batch retention or 8 MiB ordinary-file limits.
- An encrypted bounded operation journal now stores UUID artifact references, revision-checked state, process ownership and aggregate reservations. It rejects live-owner takeover, asynchronous transaction callbacks, invalid completion, held-artifact retargeting and staged cancellation. First initialization publishes a complete SQLite database without overwriting an existing one; recovery removes only the authenticated empty initializer's extra hardlink. Existing damaged fixed journals and unowned temporary files are preserved. This module is not yet the public operation coordinator and its reservation ledger is not physical scratch-quota enforcement.
- A separately encrypted cold-completion proof binds the operation, prior/restored workspace IDs, exact prepared identity and archive receipt. Cold apply writes it only after final target verification; pending stages prevent reconciliation. The journal can accept a verified new workspace identity without relabelling or exposing the old transfer history. Old reservations remain charged until actual artifact cleanup. Same-workspace replay is idempotent. Historical plaintext completion receipts alone cannot authorize this change. A pending proof blocks another v2 stage and legacy v1 staging; matching cold replay reuses its original bytes. Journal ingestion commits before the proof is consumed and fsynced. A killed process between commit and consumption is recovered without a second revision or releasing reservations.

### Catalog storage integration

New catalogs persist an optional, page-aligned physical main-database ceiling; old two-field logical-limit headers still open without rewriting. Each created or reopened connection checks its 4 KiB pages and page limit. Reads bound encrypted headers and entries in the same SQL statement before they reach JavaScript. Ordered iteration filters identities before loading payloads. A full SQLite database produces a typed capacity failure and leaves the previously admitted contents intact, including after automatic transaction rollback.

The catalog's main connection disables and verifies cache spilling; each insert contains one bounded entry. Complete bill-graph lookups use a separate in-memory SQLite database capped at 64 MiB. Thus graph checking does not grow the main catalog or force a large dirty main-database transaction. The new `catalogStorageBudget` includes main pages, journal page-record overhead and sector padding for this connection policy. It must not be reused for the spilling prepared/builder connections. This is component accounting, not aggregate disk enforcement. The lookup cap can refuse a graph before sealing; it does not discard or truncate records. Reference: [SQLite rollback journal format](https://www.sqlite.org/fileformat.html#the_rollback_journal) and [cache spilling](https://www.sqlite.org/pragma.html#pragma_cache_spill).
