# Retained mail implementation and verification

Status: integrated source and fresh unsigned macOS arm64 package verified on 21 September 2026. This is local implementation evidence, not Windows or customer acceptance. Latest package: `outputs/mail-retention-2026-09-21/package/mac-arm64/RealBud.app`; `/Applications/RealBud.app` is unchanged.

## Resulting behavior

Mail now uses six individually encrypted workflow record kinds: register, permanent task head, scan receipt, source bundle, prepared input and migration origin. The earlier 2,000-task, 1,000-receipt and aggregate journal-byte admission limits are removed. Completed tasks, failed/interrupted attempts, old sources and staff decisions are retained rather than pruned. Scan/model budgets stay bounded: 100 threads, 500 messages and 20 pages per acquisition; five batches of 20 for morning preparation; existing source/input and per-record size checks remain.

Legacy migration validates the complete source graph and commits atomically. Original files stay intact with logical origin fingerprints that survive different-key restore. Prepared bindings retain their actual input, including the migration-era input when a later review overwrites the worker projection. Missing or conflicting records hold recovery. Migration and graph checks read source bundles incrementally rather than accumulating every decoded bundle.

Acquisition intent records a process owner before provider access. A second service cannot interrupt a living owner's scan or take its work. A confirmed exited owner becomes interrupted; original coverage warnings remain. Process liveness is conservative: inaccessible or reused PIDs do not automatically grant takeover. Close waits for the owned collection to settle. Mail has its own logical revision; unrelated job-receipt writes cannot invalidate a proposal's mail authority epoch.

The HTTP contract separates metadata/counts, bounded filtered task pages, scan-history pages and exact item/source reads. Continuations bind to the mail revision and query; stale edits and continuations return conflicts. Fresh reads create no mail records, so viewing an unused workspace does not disqualify it from restore. Morning completion uses outstanding work counts, not the number of historical completed tasks.

Mail and bill-source views search retained tasks, load small pages and preserve open edits and off-page selections. Failed source reads keep prior evidence. Explicit discard controls receive keyboard focus. An uncertain invoice proposal keeps its same request identifier; a lost-response test confirms the deterministic worker runs once. A separate follow-up is still needed for explicit reconciliation of an intent that never received a worker run, including recovery after closing the tab.

## Measured loading and build identity

One fictional macOS/Node24 workload containing 2,100 tasks and 1,022 receipts initially took 4,354 ms for cold metadata, 153 ms warm and 231 ms for a 20-item page. Validation now holds at most one bounded decoded source bundle; metadata caches only counts/latest pointers under the database change token. Rollback, independent writes and snooze expiry invalidate the correct state. The same fixture measured **529 ms cold, 0.10 ms warm and 74 ms per page** afterward. These single local observations are not an office concurrency, Windows, memory-ceiling or latency SLA.

## Remaining capacity and operating gates

Backup v1 still refuses more than 5,000 physical workflow records or its existing file/aggregate byte bounds. Normalized records count individually, so removing live mail caps does not provide indefinite backup capacity. Streamed backup v2 remains unimplemented; its catalog must reuse the normalized mail graph reader. Per-record bounds, entity history limits and the 1,000-property book bound remain explicit.

Real Gmail OAuth/coverage, customer bank CSV pairs and REI Cloud acceptance, current Windows installation/ACL/DPAPI/UI, real macOS keychain behavior, signed distribution, long office/sleep/reconnect operation and deployed managed billing need separate evidence. Keys and paid service enforcement belong to the managed server; a local admin password cannot prevent a machine owner from altering local software.
