# RealBud end state

The finished product, so individual decisions can be checked against one picture.
Owner-confirmed 2026-09-17. Companions: `docs/TEAM-DECISION.md` (the team
question), `docs/OFFICE-LIFECYCLE.md` (setup → offboarding).

## The outcome we are aiming at

Not "a better agent". The outcome is:

> **A property-management office principal says yes to a pilot without
> hesitating, and the office is still using RealBud on day 90.**

Everything below serves that. It is worth stating because it reorders the
backlog: capability is not the current constraint, and never was. The constraint
is that no client can install the product yet.

## What RealBud is, in one sentence

A supervised weekday desk for Australian residential property managers. The PM
talks to RealBud, RealBud does the routine work, and it only reaches someone else
when asked — and never sends a notice or moves trust.

**Not** a PMS. Not Hermes. Not a general assistant. Not for sales agents,
tenants, or DIY landlords.

## The end state

```
   WHO EXISTS / WHO PAYS                       WHAT THEY CAN DO
   ────────────────────                        ─────────────────
   realbud.app  (website = directory + till)
   ├─ identity + billing owner                 Desk     — the book, arrears, drafts
   ├─ rate card acceptance                     Ask      — one Bud, per seat
   ├─ office → one Composio project            Schedule — named loops, office clock
   ├─ minimum supported version   ◄── GAP      You      — identity, sources, lifecycle
   └─ operator console            ◄── GAP

   THE WALL  ══════════════════════════════════════════════════════
   website holds:  billing, the ORG key, one pr_… id per office
   website never:  the client's ak_ key, the book, tenant data,
                   anything that can move trust

   ┌─ OFFICE OF ONE — the product, shippable, no server ───────────┐
   │  Mac ─ seat ─ Bud(property-<seat>) ─ encrypted book           │
   └───────────────────────────────────────────────────────────────┘
                          │ joins (explicit, device-enrolled)
                          ▼
   ┌─ OFFICE OF MANY — an add-on, needs a shared Postgres ─────────┐
   │  shared:  cases ❘ claims ❘ templates ❘ membership            │
   │  local:   books, Ask, sources, schedules, worker memory       │
   └───────────────────────────────────────────────────────────────┘
```

## Why the website is a directory and a till, not a data processor

This is a stronger claim than most products in the category can make, and it is
already true in code rather than aspirational:

| Secret / data | Where it lives | Verified |
|---|---|---|
| Client's Composio `ak_` key | the client's Mac, `~/.realbud/config.json` (0600) | `server/config.ts` |
| The book | the client's Mac, AES-256-GCM | `server/desk-crypto.ts` |
| Book key | OS keychain, wrapped by `safeStorage` | `electron/main.mjs:151-196` |
| Per-seat worker memory | one Hermes profile per seat | `server/hermes-profile.ts` |
| Org key (ours) | nowhere yet — owner-only env var | `server/composio-project.ts` |

The website can bill an office and revoke an office without ever being able to
read an office. That is the story, and it is worth protecting: every future
feature should be checked against "does this pull tenant data onto the website?"
If it does, the answer is no.

## The window model (unchanged, and load-bearing)

Four windows: **Desk · Ask · Schedule · You**. One Bud. Pinned Hermes profile
`property` is headless; RealBud owns the visible window. Never Hermes.app.

## What is done, what is not

**Done and verified** (2,594 tests passing at time of writing)

- Office-of-one desk: book, arrears, owner letter, drafts, schedules
- Per-seat isolation: one Hermes profile and one book per seat
- Composio project lifecycle: provision, rotate, decommission with upstream
  credential revocation (fail-closed)
- Office setup walkthrough, derived from the one office contract
- Retention validator and the wind-down eligibility guard

**Not done — and this is the critical path**

1. **Minimum supported version.** The desktop talks only to its own local server,
   so nothing can tell an old build it is unsupported. Needs a hosted endpoint on
   realbud.app. This is why 0.1.18 clients are a live problem.
2. **A shippable release.** 0.1.19 is built and signed but **not notarized**, so
   Gatekeeper refuses it. `/download` serves 0.1.18, which predates the office
   routes entirely. Owner-only unblock: `pnpm notary:store`.
3. **Operator console.** Margins return 503; there is no per-office provisioning
   path in the website.
4. **Wind-down completion.** Stage persistence, an operator key-destruction
   command, and only *then* a retention control in You. A knob before something
   acts on it would be a lie.

## Ordering principle

Ship the **reversible** things first. An independent office can join later; an
office whose data already landed in shared storage cannot un-share it. This is
why the office-of-one ships and the shared layer waits.

## Standing constraints

Never send. Never move trust. Never invent a legal clock. No extra Buds. Four
windows only. Never launch Hermes.app or edit Hermes source. One Composio project
per office regardless of seats. The website never holds the client's `ak_` key or
the book. Built is not live — evidence over opinion.
