## Decision

Build **Approach B now**: RealBud remains the product and authoritative control plane around one pinned, headless Bud worker. Bud may reason broadly, but it receives no ambient mutation, browser, scheduler, channel, or shell authority. Every consequential outcome becomes an exact, revision-bound proposal; **Allow** is the only execute control for Bud-generated work.

### Ask execution topology

```text
PM outcome in ordinary language
            │
            ▼
  Bud understands + decomposes
            │
            ▼
server-owned capability snapshot ── ready / practice / setup / gated / unavailable
            │
            ├── answer or evidence check (no state change)
            ├── one RealBud proposal ──▶ Desk mirror ──▶ PM Allow/Deny
            │                                      │
            │                                      ▼
            │                          owning Desk/Schedule/You command
            │                                      │
            │                                      ▼
            │                            receipt / failure / effect unknown
            └── missing adapter ──▶ prepare safe parts + name exact missing step
```

The product can therefore feel open-ended without an open-ended authority plane. New usefulness lands as a named adapter with input scope, owner, authorization level, idempotency/recovery behavior and a PM-language receipt. A connector, CLI or CUA driver is implementation machinery behind that adapter; it is never itself the user-facing capability.

| Requested outcome | Current execution rule |
|---|---|
| Review/import a file or screenshot | PM-selected resources only; stage Desk work |
| Run/change a routine | typed code-owned routine; review card; Allow |
| Change book/shop settings | bounded field diff; review card; Allow |
| Prepare approved portal wording | exact case + proposal hash + one-use authorization; Allow; human Submit |
| Connect mail/calendar | human-owned setup; no success claim until adapter-owned verification |
| Use a CLI | only through a future isolated task adapter; never the PM's ambient host shell |
| Generic computer task | requires a trained, case-bound adapter and receipt; no arbitrary desktop session |
| Send/pay/statutory work | permanently forbidden or licensed-person escalation |

## Problem Statement

Australian property managers lose time to repeated checks, inbox interruptions, data re-entry, drafting, and follow-up spread across a PMS, email, portals, and desktop applications. A general-purpose agent can technically touch those systems, but exposing its raw tools, channels, or scheduler would make onboarding confusing and would give untrusted content too much ambient authority.

RealBud already has a functional supervised desk: a native four-place UI, encrypted PM records, Desk proposals and decisions, named routines, a zero-terminal worker bridge, model-optional book intake, and a bounded fake-portal handoff. The remaining MVP problem is not to invent another agent platform. It is to turn those pieces into one reliable path from PM request or fresh source evidence to useful work, while preserving human control and making the first external PM easy to onboard.

## Demand Evidence

There is credible category pain but not yet first-party product validation:

- MRI Software's 2024 Australian/New Zealand property-management research reports that 47% of property managers work more than 41 hours per week and 54% report mental-health struggles. This supports the workload problem, not RealBud's specific solution.
- PropertyMe already markets AI and automation for arrears reminders, maintenance updates, lease communications, vacate workflows, rent-review reminders, bills, and email replies. Happy-path automation is therefore table stakes. RealBud's proposed wedge is supervised exception handling and cross-system follow-through.
- RealBud has extensive technical proof in its demo book and walkthrough, but no named external PM has yet demonstrated repeated use or willingness to pay.

Using the founder's own sanitized property data is appropriate for controlled technical validation. It must not be presented as customer validation, a live agency book, or permission to bypass the pilot contract.

## Status Quo

The PM's legal and money record remains the PMS. Routine work begins in exports, email, phone notes, or portals; the PM works out which property and person are involved, checks current facts, drafts a response or update, re-enters it into the PMS, and follows up later. Native PMS assistants can be smoother for cases already inside their system, but requests that begin in an inbox, a non-integrated portal, or an incomplete file still require manual coordination.

RealBud currently covers two useful loops—morning money and owner letters—plus book intake, Desk decisions, Ask-to-Desk drafts, a bounded fake portal and a source-built/pilot-gated Telegram Pocket adapter. It does not yet have a fresh paid-model image test, inbound mail triage, live named-PM Pocket enrollment, a named agency integration, or a self-serve installer suitable for an unknown machine.

## Target User and Narrowest Wedge

The initial user is one Australian residential property manager at one desk, onboarded directly by the founder. The first paid-worthy job is:

> Turn one fresh source item or PM request into a correctly scoped case, evidence-backed answer or editable proposal, and a safe next step—without the PM reconstructing context across systems.

The narrowest initial workflow is the existing morning-money desk plus a vertical composer that can answer from the current book, stage book intake, and stage one supported courtesy draft. Existing Desk/Schedule controls continue to run the two shipped loops. The first differentiating expansion is one read-only inbound mailbox feeding `inbound-triage` cases and reply drafts. Pocket's source adapter already reuses the broker, but live enrollment, live vendor computer use and Computer History remain evidence-gated; none is a prerequisite for loading the first PM's book.

## Constraints

- One PM, one Bud, and only Desk, Ask, Schedule, and You in the desktop navigation. Pocket is a transport projection into Ask, not a fifth surface, second session or state owner.
- RealBud owns identity, UI, persisted state, schedules, permissions, and audit. Hermes remains pinned and headless; its raw gateway, cron, tools, commands, and branding are never exposed to the PM.
- No sending, paying, trust work, statutory drafting, invented legal clocks, auto-approval, or always-allow. `POST /api/desk/drafts/:id/send` remains unconditionally forbidden.
- The PMS remains the legal and money authority. Notes and later Computer History are untrusted context, never evaluation authority.
- Browser work is case-scoped, exact-origin, expiring, and bounded to preparation; the human performs Submit.
- Recovery mode pauses writes, schedules, and browser work. Partial or uncertain external effects remain visible as unknown.
- The first live portal remains blocked on all eight fields in [`docs/PILOT-CONTRACT.md`](../PILOT-CONTRACT.md) and a vendor test account.
- Existing dirty-tree work and shipped behavior are preserved; this design does not authorize unrelated refactoring.

The permanent product rules and forbidden work are defined in [`docs/GOAL-PROMPT.md`](../GOAL-PROMPT.md). “Trust work” means trust-account transfers, disbursements, reconciliation, or payment. “Supported courtesy” means non-statutory wording carrying RealBud's mandatory disclaimer; it never means a notice.

## Premises

1. **One capable worker is enough for the MVP.** New PM workflows should arrive as typed evidence adapters and brokered operations—not new agents.
2. **Maximum usefulness does not require ambient authority.** Bud can reason over rich case context while RealBud owns every allowed operation.
3. **The product unit is a completed PM job, not a chat response.** Conversation is the front door; evidence, proposal, decision, and closure are the durable product.
4. **The current app is the MVP foundation, not a prototype to replace.** The fastest route is a funded live test and a thin broker over existing commands.
5. **Own-property testing proves machinery only.** A named PM and real source are required to prove value, onboarding, vocabulary, and workflow frequency.
6. **Approach C is earned by workflow evidence.** Optional future-looking fields and a generic plan engine would slow the MVP without making today's single-step proposals safer.

## Industry Check

The recommended direction matches current primary guidance without relying on vendor-specific frameworks:

- OpenAI recommends maximizing a single agent first, adding well-defined tools incrementally, combining guardrails with authentication and access control, and using human intervention early and for high-risk actions: <https://openai.com/business/guides-and-resources/a-practical-guide-to-building-ai-agents/>.
- Anthropic recommends starting with the simplest pattern that works and adding complexity only when it creates measurable value: <https://www.anthropic.com/engineering/building-effective-agents>.
- Anthropic's trustworthy-agent guidance emphasizes meaningful human control, transparency, privacy, constrained permissions, and layered defenses against prompt injection: <https://www.anthropic.com/research/trustworthy-agents>.

This does not mean every competent team would choose identical schemas. It means the consensus architecture is recognizably the same: one narrow agent, explicit tools, authoritative application-side permissions, human intervention at consequential boundaries, traces, and evals before more autonomy.

## Approaches Considered

- **Approach A — thin Hermes shell:** rejected because it would duplicate product surfaces, expose generic commands and permissions, and make untrusted channels part of the authority plane.
- **Approach B — RealBud capability broker:** chosen because it reuses the shipped Desk, command handlers, decisions, handoff authorization, computer lease, and worker bridge while keeping one product boundary.
- **Approach C — resumable operations kernel:** deferred until real workflows repeatedly require dependent multi-step execution, restart-safe resumption, and partial-success recovery.

## Now: Immediate Validation and Slice 1

Only this section is implementation scope for the next build. The later roadmap is informative and does not block the first named-PM pilot.

### Slice 1 architecture

```text
Desktop Ask
     |
server-authenticated input + durable receipt
     |
RealBud resolves current case/evidence and constructs a bounded prompt
     |
one headless Bud (no mutation/browser/scheduler/channel tools)
     |
strict AgentOutcomeV1 decode + evidence post-validation
     |
answer / need context / refusal / exact Desk proposal
                                      |
                         PM edits and taps Allow
                                      |
                      existing atomic Desk command
```

There is no ambient model-selected tool router in Slice 1. RealBud chooses the fixed product-mode context builder from the current Ask scope and supplies descriptive capability status, not credentials or authority. The model can return ordinary prose, the existing versioned intake outcome, or one exact `realbud.propose-action.v1` request from a closed single-step catalog. RealBud—not the model—resolves ids/revisions/authorization, authors the review card and calls an existing owner command only after Allow. Unknown output, fields or kinds fail closed. The shipped `prepare-handoff` operation may invoke only the existing exact approved adapter after that Allow; it does not mount CUA or browser tools into the conversation. Later mail/history connectors ingest evidence before the model call, and live CUA still requires the named pilot contract.

### Authoritative input and durable interaction receipt

The client submits `InteractionInputV1`; the server derives identity, channel, timestamps, and the durable request ID:

```ts
type InteractionInputV1 = {
  schemaVersion: 1;
  idempotencyKey: string;        // UUID v4 reused only for transport retry; logical Retry gets a new key
  text: string;                  // UTF-8, 0..65,536 bytes; attachment-only is allowed
  uploadIds: string[];           // 0..4 actor-bound, unclaimed upload references
  context: { caseId?: string; propertyId?: string };
  continuation?: {
    requestId: string;
    revision: number;
      token: string;
  };
};

// Reject when text.trim() is empty AND uploadIds is empty.

type InteractionState =
  | "received"
  | "running"
  | "awaiting-context"
  | "completed"
  | "failed"
  | "cancelled";

// Public response; contains no token hash, fingerprint, or internal run fence.
type InteractionReceiptV1 = {
  schemaVersion: 1;
  requestId: string;             // server UUID v4
  state: InteractionState;
  revision: number;
  outcomeKind?: AgentOutcomeV1["kind"];
  proposalId?: string;
  errorCode?: BrokerErrorCode;
  resultMessageId?: string;
  receivedAt: number;
  updatedAt: number;
};

type InteractionResponseV1 = {
  receipt: InteractionReceiptV1;
  resultMessage?: Message;
  continuation?: { token: string; expiresAt: number }; // response-only
};

// Internal stored record; never accepted from or returned wholesale to a client.
type StoredInteractionV1 = InteractionReceiptV1 & {
  idempotencyKey: string;
  fingerprint: string;
  actorId: "pm";                 // derived from local authentication
  channel: "desktop";            // derived from the server route
  threadId: string;
  userMessageId: string;
  continuationOf?: string;
  continuationTokenHash?: string;
  continuationTokenCiphertext?: string; // local encryption; never logged
  continuationExpiresAt?: number;
  runTokenHash?: string;
  retryOf?: string;
  retrySnapshot: {
    normalizedText: string;
    context: { caseId?: string; propertyId?: string };
    attachmentHashes: string[];
    retryUploadIds: string[];
  };
};
```

Store internal records in the existing `messages-<threadId>.json` object under a new `interactions` map; old files decode with an empty map. The transcript stays the conversation record. `server/store.ts` owns one atomic write for the user message plus initial record, and one atomic write for the assistant result message plus completed record. `resultMessageId` lets replay/restart return the durable answer, question, refusal, escalation, or proposal card rather than only its kind.

The single pinned Bud has a **global capacity of one product-mode turn**, even if legacy task records exist. A second Ask request from any thread returns `BUSY`; the composer may hold one local unsent message but the server does not queue hidden work.

Canonical fingerprint input is `schemaVersion`, server actor/channel, normalized LF text in Unicode NFC, ordered claimed-upload content hashes, sorted context keys, and continuation parent ID/revision/token hash when present. Emit those fixed fields in schema order as UTF-8 JSON with no insignificant whitespace and hash with SHA-256; prefix the stored value `v1:`. Identical idempotency key plus identical fingerprint returns the existing receipt/result. The same key with a different fingerprint returns `REPLAY_CONFLICT` and creates nothing.

When Bud asks for context, the record becomes `awaiting-context` and `InteractionResponseV1.continuation` carries a random single-use token. Store its hash plus locally encrypted ciphertext; never put it in logs or the assistant message. It expires at the earlier of 30 minutes or the earliest linked Evidence `staleAt`. An authenticated local reload may reissue the decrypted token until expiry. A reply uses a new idempotency key plus parent request ID, expected parent revision, and token. One atomic thread-store write consumes/erases the token, completes the parent, and creates the child record. A missing, reused, cancelled, expired, or stale token returns `REVISION_CONFLICT`. Expiry releases transient attachments. A normal message without this tuple starts a new interaction.

`POST /api/interactions/:id/cancel` is valid only for `received`, `running`, or `awaiting-context`; it atomically marks `cancelled`, increments the revision, releases unpromoted staging, and best-effort interrupts the worker. Each model dispatch carries a random run token tied to the interaction revision. Timeout, cancellation, or restart increments the revision and clears that token before interrupting; a late response whose token/revision is no longer current is discarded before any message or Desk write.

`POST /api/interactions/:id/retry` accepts a new UUID-v4 idempotency key and no editable content. It reconstructs the exact normalized text/context from `retrySnapshot` and atomically transfers still-valid retained uploads to a child record with `retryOf`. To change text/context, the PM sends a normal new message. Retryable image bytes are retained for 15 minutes or one retry, whichever comes first; non-retryable, successful, cancelled, expired, or consumed bytes are deleted. If the bytes are gone, the UI says **Attach image again** rather than offering automatic Retry.

On startup, validate/decrypt the stores and establish recovery state first; reconcile durable Desk proposals/Decisions by origin/request ID second; complete any matching in-flight interaction third; fence only the remaining `received`/`running` records as terminal `TURN_INTERRUPTED` fourth; expire continuations fifth; then garbage-collect staging. No model turn is silently resumed. `awaiting-context` remains only while its encrypted token and expiry are valid. `MODEL_UNAVAILABLE`, `MODEL_TIMEOUT`, `AGENT_OUTPUT_INVALID`, and `TURN_INTERRUPTED` expose Retry only while the retry snapshot is usable. `REPLAY_CONFLICT`, `FORBIDDEN_ACTION`, and validation failures are terminal until input changes. A persistence-uncertain result enters recovery and exposes restart, not Retry.

Normative lifecycle:

| Current | Legal next state | Atomic persistence boundary | Cleanup | PM-visible result |
|---|---|---|---|---|
| new | `received` | user message + stored interaction in one thread write | retain owned staging | message appears |
| `received` | `running`, `cancelled`, `failed` | state/revision/run-token update in one thread write | release on cancel/non-retryable failure; otherwise bounded retry retention | Working, Stop, or safe error |
| `running` | `completed`, `awaiting-context`, `failed`, `cancelled` | non-proposal result message + record in one write; proposal commits to Desk first, then result/record | release raw staging after durable fields/hashes exist | answer/card, question, Retry, or Stopped |
| `awaiting-context` | `completed`, `cancelled`, `failed` | token consumption + parent completion + child `received` in one write, or terminal update | release at consumption/expiry/cancel | reply field, Stopped, or Context expired |
| `completed` | none | terminal | no transient staging | durable result by `resultMessageId` |
| `failed` | none | terminal; Retry creates linked new record | retain usable inputs for 15 minutes/one retry; recovery-uncertain exposes restart | Retry or Attach again only when valid |
| `cancelled` | none | terminal | release and discard late run token | Stopped |

No transition mutates a terminal record. UI reload renders directly from the stored state/result pointer; telemetry never substitutes for persistence.

### Attachment boundary

- `POST /api/interactions/uploads` accepts one authenticated local binary upload with declared safe filename/MIME and streams it directly to staging under the limits below; it returns an opaque `uploadId`. The 1 MiB JSON-body cap does not apply to this binary route.
- An upload begins actor-bound and unclaimed with a 15-minute expiry. During interaction acceptance, the global broker mutex validates every upload, creates the server request ID, provisionally claims uploads to it, and atomically persists the initial message/interaction. If initial persistence fails, the handler releases/deletes the provisional claims; startup garbage collection deletes a claim whose request does not exist. Repeating the same interaction idempotency key returns the same claims and never double-claims.
- Existing inline paste remains capped at 512 KiB.
- Slice 1 image intake accepts JPEG, PNG, or WebP only, at most four files, 10 MiB each and 20 MiB total.
- Store accepted files under `REALBUD_DATA_DIR`; after claim, each staging record binds request ID, actor, SHA-256, MIME, byte size, and expiry. Generate safe names. Never place an arbitrary user-supplied filesystem path in a model prompt.
- Reject images above 25 megapixels or 8,192 pixels on either edge; resize the inference copy to a 2,048-pixel longest edge without enlarging. Preserve the original content hash as provenance.
- Enforce 20 MiB per request and 100 MiB aggregate staging quotas. Startup and hourly garbage collection remove expired 15-minute upload/retry records, cancelled/non-retryable files, orphan claims with no interaction, and any staging file older than a 24-hour hard failsafe.
- Delete transient staged bytes after completed/non-retryable-failed/cancelled processing. For book intake, persist only the source message ID, ordered attachment hashes, extracted fields, and optional safe filename—not raw bytes or a reusable upload ID. Retryable bytes follow the 15-minute/one-retry rule above. Slice 1 has no raw-file promotion into Desk evidence.
- MIME signature, declared MIME, extension, decoded dimensions/pixels, file count, ownership, expiry, and byte limits must agree. Unsupported, orphaned, cross-request, or malformed images fail before the model call.

### Closed model outcome

```ts
type MissingFieldV1 =
  | "property"
  | "case"
  | "current-evidence"
  | "tenant"
  | "rent-facts"
  | "attachment-readable"
  | "user-intent"
  | "licensee-decision";

type AgentOutcomeV1 =
  | {
      schemaVersion: 1;
      kind: "answer";
      answerClass: "book-factual";
      text: string;               // 1..4,000 Unicode characters
      evidenceIds: string[];      // 1..20 current scoped Evidence IDs
    }
  | {
      schemaVersion: 1;
      kind: "need-context";
      question: string;           // 1..500 characters
      missing: MissingFieldV1[];  // 1..8 unique values
    }
  | {
      schemaVersion: 1;
      kind: "propose";
      action: ActionIntentV1;
    }
  | {
      schemaVersion: 1;
      kind: "escalate";
      reasonCode: "licensee-required" | "ambiguous-property" | "stale-evidence" | "safeguard-present";
      text: string;               // 1..1,000 characters
    }
  | {
      schemaVersion: 1;
      kind: "refuse";
      reasonCode:
        | "forbidden-send"
        | "forbidden-trust"
        | "forbidden-statutory"
        | "unsupported-action"
        | "insufficient-authority";
      text: string;               // 1..1,000 characters
    };

type ActionIntentV1 =
  | {
      schemaVersion: 1;
      kind: "stage-book-intake";
      item: {
        address: string;           // trimmed, 1..160 characters
        tenantName: string;        // trimmed, 1..120 characters
        tenantPhone: string;       // trimmed, 8..32 characters
        weeklyRentCents: number;   // integer, 1..10,000,000
      };
    }
  | {
      schemaVersion: 1;
      kind: "draft-courtesy";
      caseId: string;
      propertyId: string;
      evidenceIds: string[];       // 1..20, current case evidence only
      body: string;                // trimmed, 1..1,000 characters
    };
```

`stage-book-intake` stages exactly one property per model interaction. RealBud binds provenance from the server-owned user message and attachment hashes; the model never selects source IDs. Multi-property paste continues through the existing deterministic bulk parser, not this model action. The handler reserves the normalized address across active Properties and unexpired open book proposals and creates one proposal with `origin { requestId, itemOrdinal: 0 }`. A duplicate returns server-generated `BOOK_DUPLICATE` with an optional `{ existingKind: "property" | "proposal", existingId }` only after the same local PM is authorized to view that record; the model never invents the reference. Deny or seven-day expiry releases the reservation. Allow atomically rechecks address uniqueness and the 200-property cap; if capacity or identity changed, it adds nothing and returns `BOOK_DUPLICATE`, `REVISION_CONFLICT`, or `BOOK_CAPACITY`. Slice 1 book-proposal fields are not edited in place: the PM denies and restages a correction, preserving provenance.

`draft-courtesy` calls the existing Ask proposal path after server validation; the server reapplies the mandatory disclaimer and derives recipient/channel/current facts. The model cannot supply a recipient, channel, legal timing, send flag, handler name, URL, tool, or command.

All schemas reject unknown fields. Unscoped greetings, acknowledgements, and RealBud product help are served from deterministic local templates and stored like any completed interaction; they do not call Bud or claim book facts. A scoped model turn may return only evidence-backed `book-factual`, `need-context`, proposal, escalation, or refusal. An answer with no evidence fails post-validation. Ask requests schema-shaped JSON from Bud; if the first response is malformed, the broker may make one bounded no-tool repair call containing only the schema and malformed output. A second failure returns `AGENT_OUTPUT_INVALID`. Every evidence ID is checked against the exact context sent to the model, and every action is revalidated from current server state. No model claim becomes authority.

Inference is bounded to 20 projected Evidence records and 32 KiB of structured case context; no raw history bodies enter the prompt. The primary call is capped at 20,000 input tokens, 2,000 output tokens/16 KiB, and 90 seconds. One repair is capped at 4,000 input tokens, 1,000 output tokens/8 KiB, and 30 seconds; total wall time is 120 seconds. The founder configures a pilot ceiling of AUD 0.25 estimated cost per interaction for the selected model; if pricing is unavailable, image/repair calls require an explicit pilot override and cost is reported as unverified rather than silently unlimited.

### Evidence rules

For a factual answer or courtesy proposal, an Evidence ID is usable only when all are true:

1. It exists and belongs to the scoped case/property/tenancy.
2. `observedAt` is present, `now < staleAt`, and the linked Source's configured `freshnessMs` agrees with that window.
3. It is the Evidence referenced by the current `MoneyPosition` projection and that projection is `current`.
4. Its authority is `pms` for live work or `demo` for explicitly labelled validation. `legacy-unverified` can only produce a hold.
5. No equally current authoritative observation disagrees. Same-source newer `observedAt` supersedes older evidence; disagreement between equally current sources becomes `conflicted` with no model-selected precedence.

`stale`, `conflicted`, `requires-recheck`, unmatched, ambiguous, reversed, or missing observations produce `need-context`/`escalate`/hold, never actionable wording. Notes may colour draft prose only after deterministic factual evaluation and never change these rules.

### Proposal origin, Allow, replay, and recovery

Add a backward-compatible optional origin to V3 cases/proposals and book proposals:

```ts
type AskOrigin = { kind: "ask"; requestId: string; itemOrdinal?: 0 };
type RevisionAuthor = "bud" | "pm" | "legacy-unknown";
```

Strict decoders accept absent origin for existing data. Existing revisions decode with `author: "legacy-unknown"` and `evidenceIds: []`; new Slice 1 revisions require both fields. This is a backward-compatible read default, so no version bump or bulk rewrite is required. `requestId` is unique within Desk. If Desk commits a proposal but patching the interaction receipt fails, startup reconciliation finds the proposal by `origin.requestId` and completes the receipt. If no durable proposal exists, the receipt becomes retryable `failed`. The transcript is diagnosis; Desk remains authority.

Every `ProposalRevision` stores `author: RevisionAuthor` and the evidence IDs used when Bud created it. A PM edit appends a new revision with `author: "pm"`; it never overwrites Bud's grounded revision. The UI labels it **Edited by you** and changes evidence copy from “supports this wording” to “sources available when this draft began.” Before Allow, the server rechecks current evidence, locked factual fields, mandatory disclaimer, and deterministic forbidden-action gates. PM-edited prose is never represented as model-verified; recipient, channel, balances, dates, and legal status remain non-editable server fields.

Allow submits authenticated PM identity, Desk expected revision, proposal ID, exact `ProposalRevision` ID/hash, and an idempotency key. Replay semantics are exact: identical key and payload returns the prior durable decision/result; the same key with different payload is `REPLAY_CONFLICT`. Missing, denied, superseded, stale, already-consumed, wrong-case, or wrong-operation proposals fail before mutation.

The Desk command transaction must:

1. capture the current recovery epoch and clone the affected in-memory state;
2. validate permission, evidence, revision, proposal, and idempotency;
3. append the `Decision` and apply the internal state change to one candidate;
4. recheck the recovery epoch immediately before atomic replacement;
5. encrypt, write, fsync, read/validate, rename, and fsync the directory;
6. publish UI state only after the durable outcome is known.

A pre-replace failure restores the clone and persists no Decision. If replacement landed but final durability is uncertain, keep the landed state visible, enter recovery pause, and reject further writes until restart, matching the shipped bulk-persist recovery rule. An audit/receipt patch after the Desk commit is reconciled by decision/request ID and cannot repeat the command.

Scheduled loops need no per-tick Allow because code limits them to reads, evaluation, holds, and new proposals; they cannot send, pay, launch CUA, or approve. A direct Schedule form/toggle is an explicit PM configuration action. Any later Bud-generated clock change is itself a proposal requiring Allow.

### Stable broker errors

| Code | Meaning |
|---|---|
| `INVALID_INPUT` | Envelope, schema, attachment, or field validation failed |
| `BUSY` | The single Bud worker already has a product-mode turn in flight |
| `MODEL_UNAVAILABLE` | No funded/healthy pinned worker model |
| `MODEL_TIMEOUT` | Bounded turn or repair deadline exceeded |
| `TURN_INTERRUPTED` | Restart or explicit Stop fenced off the prior run |
| `AGENT_OUTPUT_INVALID` | Strict outcome failed after one repair |
| `EVIDENCE_STALE` | Current authoritative evidence requirement failed |
| `BOOK_DUPLICATE` | Normalized address already belongs to an authorized Property/open proposal; nothing was staged/added |
| `BOOK_CAPACITY` | The 200-property limit changed or is full; nothing was added |
| `COST_LIMIT` | The configured pilot interaction budget would be exceeded |

## Privacy Gate Before Real Tenant Data

Sanitized/demo data is allowed during the pre-code baseline and Slice 1 acceptance. Before an external PM imports real tenant or owner information:

1. Record agency/pilot permission, permitted data classes, model provider, provider data-handling terms, retention period, and who may operate the machine.
2. Disclose which content leaves the machine for model inference; default to the minimum case context and never send the whole book.
3. Enforce `retentionDays` for transcripts, transient attachments, evidence payloads, and backups. Evidence referenced by an open case/Decision/Handoff remains; once closed and expired, purge the payload and retain only a non-sensitive tombstone ID/hash/source/time needed for integrity.
4. Delete transient staged files on completion/failure/cancellation and provide an explicit, confirmed local book/pilot deletion path. Deletion must cover derived caches and expired backups.
5. Protect Desk and provider credentials with OS-backed storage or an explicitly documented pilot control; never log or sync keys. The existing T15/T16 privacy/key gaps must be closed or the pilot stays sanitized.

Email, attachments, web pages, screenshots, Notes, and later Computer History are untrusted data, never instructions. In Slice 1 the model has no action tools, so prompt injection cannot widen its authority. Logs contain only sanitized trace ID, stage, duration, model status, linked record IDs, and stable error code—not bodies, screenshots, raw attachments, keys, or tenant details.

This is a parallel **Privacy P0** workstream, starting after the shipped-path baseline and completing before any real-data import:

| Owner | Required work and verification |
|---|---|
| `docs/PILOT-CONTRACT.md` + You disclosure | Named permission, allowed data/provider/retention; snapshot/E2E proves the PM sees it before import |
| `server/retention.ts` (new) + Desk/message stores | Reference-aware transcript/evidence/raw-payload/backup sweep; fake-clock tests cover open references, expiry, tombstones, restart, partial failure |
| `server/attachment-staging.ts` | Completion/cancel/expiry/startup cleanup and disk quotas; orphan/crash/quota tests |
| `server/desk-key.ts`, worker bridge, Electron main | OS-backed Desk secret and provider-key handling, or documented 0600/dedicated-account pilot control; tests prove keys never enter Desk, snapshots, logs, analytics, or crash errors |
| You → Delete pilot data | Explicit typed confirmation, stop worker/schedules, delete primary/derived/cache/expired-backup data, verify absence, and report anything preserved; isolated-data E2E only |

The real-data onboarding gate is one automated privacy suite plus a manual clean-machine inspection. A failure keeps the product in sanitized/demo mode; it cannot be waived by a model prompt or PM chat command.

## Later Roadmap — Explicitly Non-Blocking

Each later slice requires its own short approved design, dependencies, test matrix, and exit gate. None is part of Slice 1 readiness.

### Slice 2 — one inbound-triage source

Choose the pilot's actual mailbox and design one read-only adapter: deduplicate/thread → classify/link property and tenancy → immutable evidence → case → reply draft. No archive, send, mark-read, tenant bot, or arbitrary mailbox tools. Provider auth, delta cursors, deletion, attachment retention, and prompt injection must be resolved for the chosen source before implementation.

### Slice 3 — Pocket adapter hub (source-built, live gated)

Telegram long polling and official WhatsApp Business Cloud are the two adapters. Both map one exact PM private identity to canonical Ask and manual Allow/Not now through the same revision-bound action owner. Telegram is outbound-only. WhatsApp binds a loopback signed webhook behind an agency-approved HTTPS tunnel, verifies Meta HMAC before parsing, checks the exact business-number route and PM number, claims before fast acknowledgement and stays unconnected until the Verify Token handshake. A bounded hub queue serializes channel turns against the one Ask thread. The transports store encrypted credentials separately and retain only bounded ids/digests, states and timestamps. They never automatically replay a crash-interrupted request, record lost outbound acknowledgement as `effect-unknown`, reject groups/other identities/attachments/credentials/general commands and fail closed on corrupt state. Neither can launch a generic CUA session or use a shell.

The checked-in Demo contract disables all network activity. Remaining gates are a named agency and PM, agency acceptance of each channel's privacy boundary, a stable agency-owned WhatsApp HTTPS tunnel/Meta business setup, and live send/receive/restart/stale-button/disable/ambiguity proof. Mobile attachments/voice, proactive alerts, background operation while RealBud is closed and additional platforms remain later work. Personal-account QR automation is rejected.

### Slice 4 — one live portal operation

After the eight-field pilot contract is complete, adapt one vendor test account and one closed preparation operation to the existing `HandoffAuthorization` and shared computer lease. The sequence is fresh observation → exact app/window/origin verification → permitted semantic step → observation/read-back. Non-idempotent steps are never blindly retried.

After the human performs Submit in the PMS/portal, RealBud offers **Done in PMS** or **I couldn't confirm**. The first appends a human-confirmed Handoff outcome without claiming RealBud sent it; verified read-back may append `verified`. Missing/ambiguous read-back, window closure, or timeout records `effect-unknown`. See [`docs/computer-use-integration.md`](../computer-use-integration.md).

### Slice 5 — Computer History and Approach C only if earned

Computer History may become an opt-in, case/time/app/domain-bounded Evidence adapter. It is never Bud's memory or evaluation authority; private browsing is excluded and block settings win. Do not build it until a PM identifies a repeated context-reconstruction task not solved more safely by PMS/mail evidence.

Move toward a resumable operations kernel only when all are true:

1. At least two real workflow kinds need to pause for human/external input and resume after an app restart.
2. At least one has three or more dependent cross-system steps where partial success needs retry, compensation, or reconciliation.
3. Five or more real runs show current proposal/handoff state reconstruction is a material failure source.

Until then, versioned requests, immutable evidence/revisions/decisions, origin request IDs, and handoffs provide the upgrade seam without speculative workflow machinery.
