## Implementation

`server/helpers/hermes-memory-windows-native.py` owns typed Win32 bindings and file handles. It accepts local fixed NTFS volumes with persistent ACLs, verifies file identity and actual security descriptors, refuses reparse points and multiply linked files, and creates new private files with their security descriptor supplied before any contents. Existing files cannot be truncated or rewritten through its write method. Unknown native errors become fixed messages. An unsuccessful close never marks the handle released.

`server/helpers/hermes-memory-windows.py` pins every ancestor directory, confines operations to one protected profile, checks content digests, and requires a host-owned mutation lock. Publication is a no-clobber rename of the verified source handle into a verified destination directory handle. Replacement checks the old bytes under the cooperative native lock, closes that target reader, then replaces the whole file. It never copies through or falls back to an in-place write. Readback uses the retained source handle and checks its new name and identity. This is not a destination compare-and-swap against arbitrary same-user writers.

The root ACL must be protected. A native-created child may inherit access only beneath a currently verified private root, and every actual ACE must still satisfy the current-user/System/Administrators policy. The separate global `windows-file-privacy.ts` policy is unchanged. Impersonated execution and unsupported storage remain held.

Deletion binds disposition to the checked handle but returns **deletion-requested**, not a terminal cleanup receipt. A pre-existing reader with delete sharing may retain the file after our handle closes. Journal integration must reconcile namespace absence before terminal cleanup. Likewise, an interrupted or ambiguous rename requires signed before/after reconciliation rather than repeating a mutation on assumption.

The direct Python review dispatcher now enforces the Windows hold before native imports or profile access. The host and proposal integration already enforce their own hold. The new modules are not wired into approved live memory changes yet.

## Design evidence

Handle-relative replacement follows Microsoft's [FILE_RENAME_INFO contract](https://learn.microsoft.com/en-us/windows/win32/api/winbase/ns-winbase-file_rename_info). Actual per-file security is read through [GetSecurityInfo](https://learn.microsoft.com/en-us/windows/win32/api/aclapi/nf-aclapi-getsecurityinfo). Writable source handles use write-through and checked pre/post flushes according to [CreateFileW](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-createfilew); these checks do not prove hardware power-loss durability. Full primary-source notes, admitted Hermes source hashes and dispositions are in `outputs/hermes-memory-windows-2026-09-22/`.

The unmodified admitted Hermes Windows fallback may perform an in-place overwrite after sharing failures. That persistence path must be bypassed for approved Windows memory changes; changing the upstream runtime is not the solution. Native memory semantics and interoperable target locks still need explicit integration with the owned journal and adapter.

## Windows native finding — check 7, 22 September 2026

This note records a diagnostics change and the first real native finding. No Windows acceptance has passed; the native candidate remains unproven on Windows and the production hold is unchanged.

Run 35712111382 (`windows-latest`, Windows Server 2025 build 10.0.26100, Python 3.12.10, disposable root on the `D:` work volume) passed checks 1 to 6 — including the two PowerShell-fixture cases that previously timed out, at 46.8 s and 55.1 s, inside the new 120-second budget — and then failed the seventh case, "Handle-bound same-volume no-clobber publication moves one complete file". The receipt recorded `failure_type: NativeError`, `native_failure: "unavailable"`, `handles_drained: true` and `cleanup: true`. This is the first Windows result that is a real native refusal rather than a harness timeout: the timeout fix held, and the primitive itself did not.

What the earlier receipt could not say is which native call refused and why. `native_failure` is only the fixed public category, and `"unavailable"` means solely that the Win32 code was neither 80 (`ERROR_FILE_EXISTS`) nor 183 (`ERROR_ALREADY_EXISTS`) — so a plain no-clobber destination collision is excluded, and everything else is not. Nothing in the evidence distinguishes the `CreateFileW` that opens the stage for `DELETE` access from the `SetFileInformationByHandle` that publishes it.

Changed, without relaxing any refusal, assertion or guarantee: `NativeError` now optionally carries the numeric Win32 code, a fixed primitive label drawn from the module's `PRIMITIVES` allow-list (for example `CreateFileW` or `SetFileInformationByHandle(FileRenameInfo)`) and a short fixed flags summary (for a publication, `ReplaceIfExists=…|RootDirectory=bound|NameBytes=…|Buffer=…`; for an open, the requested access mask, share mode, disposition and create flags). Every native call site in `CtypesBindings` now names its primitive, and `_fixed` preserves that detail through its re-raise instead of discarding it. Public codes, their values and `str(error)` are unchanged, so the portable ABI and policy suites still hold. The acceptance receipt records `native_error: { code, primitive, flags }` on a native failure, re-validating all three fields on the way in so an older or packaged helper cannot widen them: a value outside the allow-list or the `[A-Za-z0-9_=|]` shape is dropped, and no path, leaf name or file byte can appear.

No rename variant was changed, because the premise that check 7 might be using `FileRenameInfoEx` with `FILE_RENAME_FLAG_POSIX_SEMANTICS` is not true of this source. `CtypesBindings.rename` already uses the safest documented form: `SetFileInformationByHandle` with the non-Ex `FileRenameInfo` class (3), `ReplaceIfExists` set from the caller and therefore FALSE for a no-clobber publication, a relative leaf bound to the verified destination directory handle through `RootDirectory`, on a source handle opened with `DELETE` access. There is consequently no Ex/POSIX variant to fall back from on `ERROR_INVALID_PARAMETER` (87) or `ERROR_NOT_SUPPORTED` (50), and the no-clobber guarantee is untouched: a pre-existing destination is still refused. Adding a path-based or `RootDirectory`-free fallback would weaken the handle binding the design depends on, so none was added on speculation.

Verified on macOS only: `python3 -m py_compile` on both scripts; the four portable sibling suites (abi 19, policy 19, protocol 33, journal-io 18 — all passing, unchanged); disposable control-flow checks that the new detail survives the `_fixed` re-raise, that a path-shaped primitive or flags string and an out-of-range code are dropped to `null`, that a failing fake `CreateFileW`, rename and delete each report their own primitive and flags, and that `NativeError("password=fake").code` still collapses to `unavailable`; and the non-Windows unsupported path (exit 2, zero native checks, no `native_error` key). ## Windows native fix — check 7 is Win32 87 on a bound RootDirectory, 22 September 2026

This note records the cause of check 7 and the fix for it. No Windows acceptance has passed; the native candidate remains unproven on Windows and the production hold is unchanged.

The instrumented `windows-latest` run (Windows Server 2025, Python 3.12) passed checks 1 to 6 and failed check 7, "Handle-bound same-volume no-clobber publication moves one complete file", with the new detail: `native_error: { code: 87, primitive: "SetFileInformationByHandle(FileRenameInfo)", flags: "ReplaceIfExists=0|RootDirectory=bound|NameBytes=44|Buffer=66" }`. Win32 87 is `ERROR_INVALID_PARAMETER`, and it names the publication call, not the open. The previous note's reasoning — that the non-Ex `FileRenameInfo` class with a relative leaf bound through `RootDirectory` was the safest documented form — was wrong on one point, and the runner said so: for `SetFileInformationByHandle`, Microsoft's `FILE_RENAME_INFO` documentation requires `RootDirectory` to be NULL and `FileName` to be a fully qualified path. Root-relative renames are an NT-layer facility, reachable only through `NtSetInformationFile` with `FILE_RENAME_INFORMATION` (class 10). The kernel never saw a same-volume or collision question here; it rejected the request shape.

Design A was taken: keep the documented Win32 API and drop to `RootDirectory = NULL` with a fully qualified `FileName`. Option B, `ntdll.NtSetInformationFile`, would have kept the kernel-level binding as a pre-condition, but this module depends on no ntdll entry point anywhere else, and adding an undocumented-API dependency to the one primitive that publishes memory is a worse trade than re-expressing the binding as a verified pre- and post-condition.

Changed, without relaxing any refusal, assertion or guarantee. `CtypesBindings.rename` keeps its handle-only signature — no caller anywhere can supply a destination path — and now resolves the destination itself from the destination *directory handle* via `GetFinalPathNameByHandleW` with `FILE_NAME_NORMALIZED` (factored out as `_final_path`, shared with `file_identity`), appends the validated leaf, and passes the result through the module's existing `_path` check. `RootDirectory` is NULL, `ReplaceIfExists` is still the caller's value and therefore FALSE for a no-clobber publication, and the source handle is still the one opened with `DELETE`; the sharing mode is untouched, so the sharing-denial case keeps its meaning. The flags summary now reads `RootDirectory=null`, and `native_error` reporting is unchanged for this and every other call site.

The trade-off is that the binding to the directory *object* becomes a pre- and post-condition rather than a kernel-level pre-condition. Two things carry it. The name is resolved from the open handle as late as possible, immediately before the call, so it still spells that directory object rather than a caller's idea of it; and `Win32Native.rename` already re-reads the moved file's own canonical path afterwards and requires exact equality with the verified directory's path plus the leaf, refusing anything else as `conflict`. The residual window is between `GetFinalPathNameByHandleW` on the parent and `SetFileInformationByHandle`; if the directory is moved inside it, the post-condition fails and the publication is reported as a conflict for the caller's recovery protocol rather than accepted. As with the other post-checks in this module, a refusal at that point does not roll the move back — the journal recovery path owns that, unchanged.

Verified on macOS only: `python3 -m py_compile` on both scripts; the four portable sibling suites — policy 19, protocol 33, journal-io 18 all passing unchanged, and abi 20 passing after replacing the one test that pinned the disproven ABI. That test asserted `RootDirectory == 456` and a leaf-only `FileName`; it now asserts a NULL `RootDirectory`, the parent handle's full path plus the leaf as UTF-16 bytes, that the path came from `GetFinalPathNameByHandleW` on the parent handle with flags 0, and that a parent path which cannot be canonicalised refuses before any `SetFileInformationByHandle` call. The acceptance script's non-Windows path still exits without running a native check and writes no false pass. Nothing here is Windows evidence. The next `windows-latest` run is the only proof; checks 7 to 13 remain unrun on Windows until it passes.
