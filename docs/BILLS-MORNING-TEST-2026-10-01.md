The first attempt to run that expanded diagnostic failed at parsing before any provider access; it was rerun from a frozen syntax-checked copy.

The [pinned Composio thread schema](https://docs.composio.dev/api/tools/GMAIL_FETCH_MESSAGE_BY_THREAD_ID?version=20260915_00) declares those normalized fields but does not specify the timestamp's derivation. Its optional thread identifier is `threadId`. The [message-by-ID schema](https://docs.composio.dev/api/tools/GMAIL_FETCH_MESSAGE_BY_MESSAGE_ID?version=20260915_00) also describes a normalized result, while the [official toolkit descriptions](https://docs.composio.dev/toolkits/gmail) recommend `internalDate`. [Google's message reference](https://developers.google.com/workspace/gmail/api/reference/rest/v1/users.messages) defines the latter's inbox ordering and normal acceptance-time semantics. A format-only match cannot prove the two timestamp fields equivalent.

A third diagnostic read one exact message from the selected thread with the pinned `GMAIL_FETCH_MESSAGE_BY_MESSAGE_ID` tool and `format=full`. Both normalized message and thread identities matched. The raw `internalDate` field was still absent; the normalized timestamp matched the Date header in this observed thread. This does not establish universal timestamp derivation and is not an acceptable replacement for Gmail's receipt-ordering field. The frozen diagnostic passed **9 / 0 / 0** synthetic tests before execution.
