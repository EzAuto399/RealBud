# Connected apps and Bud tool execution — 8 September 2026

This continuation connects the PM-facing setup journey to Bud's actual MCP tool transport. It distinguishes a saved key, a checked account, discovered tools, an approved operation and a completed business task. Earlier book, Schedule and manual-run work is covered in [scheduled work](PM-SCHEDULED-WORK-2026-09-08.md).

## Implemented behavior

- **You → Connected apps** separates key storage from the last access check. Gmail and Outlook show the provider's account status and supplied identity, require a choice when multiple active accounts exist, and expose discovered tool names. Missing configuration, unavailable tools, failed checks and stale observations have explicit recovery. A saved key alone never enables email preparation.
- **Prepare email follow-ups** stages an editable Ask task for the last seven days and at most ten threads. It preserves the PM's unsent draft and attachments. The selected account is carried into the task for confirmation against the actual tool; selection does not grant access. The task asks for source-linked follow-ups and local drafts, with no sends, mailbox drafts, marking read, deletion or other mailbox changes. It does not submit itself to Bud.
- Access observations expire after five minutes. Starting preparation re-reads server status and revalidates account choice, settings and worker availability. Changing the key invalidates cached access and active connected-app brokers, including pending calls. A response from an older check cannot validate replacement settings.
- OAuth follow-up remains visible in Ask outside the optional task menu. The PM can return from the browser and check access. A provider connection record is described as metadata, not proof that a mailbox read succeeded or that particular scopes were granted.
- Hermes receives a local, authenticated MCP broker descriptor rather than the upstream consumer key. The transport performs an MCP initialization handshake and handles bounded JSON or SSE responses, including streams that remain open. Invalid endpoints, payloads and unsupported responses fail with sanitized errors.
- Tool and schema discovery and a valid connection-list request can return metadata without granting mailbox authority. Other app operations require review of the exact call once. Tool names and `readOnlyHint` do not bypass review. Remote workbench and remote shell tools are blocked. Within a broker session, identical repeated RPC requests share their outcome; changing the request body cannot reuse an earlier approval.
- Each dispatched operation has a durable receipt written first. The activity view retains recent receipts through refresh failure and distinguishes started, succeeded, failed, denied and unknown. Restart converts unfinished operations to unknown. Reviewing an unknown receipt attaches context to Ask without replaying the operation. Corrupt or unwritable history holds new operations instead of silently losing evidence. Receipts retain fixed metadata, not tool arguments, provider results, account details or credentials.
- The Hermes launch restricts configured MCP discovery with a per-host toolset selector as well as the startup skip flag. This prevents an existing Hermes profile's same-named configured server from bypassing RealBud's broker when ACP creates a session. Explicitly supplied ACP MCP servers remain available.
- Explicit MCP/API/Composio requests now reach the worker instead of the portal-job keyword shortcut. The live metadata request exposed this regression; its unapproved, unscheduled generated plan was removed with an identity check. The exact routing regression is covered by focused tests, and the actual UI retry completed tool search and schema retrieval without creating another portal plan.

## Live authorization and remaining work

Google's final Gmail consent screen remains pending the user's choice. All consent boxes were left unchecked. The current consumer connection asks for the broad `https://mail.google.com/` scope, which includes reading, sending and permanent deletion, alongside other optional permissions. No live email was read and no external write was made in this walkthrough. The in-app review boundary does not narrow the OAuth grant itself. [Google's scope definitions](https://developers.google.com/workspace/gmail/api/auth/scopes).

The documented narrower route is a developer-project Gmail auth config with `https://www.googleapis.com/auth/gmail.readonly`, followed by a new connection and a session explicitly bound to that config/account. Consumer Connect and developer projects have separate account/config boundaries; the existing consumer key cannot simply select a developer auth config. No documented consumer Connect scope override was found. A developer project credential and corresponding RealBud session wiring would be required; a new Google consent screen must still be checked before claiming read-only access. This route has been researched, not configured or tested here. [Composio project boundaries](https://docs.composio.dev/kb/guide/consumer-project-boundaries-and-auth-selection), [scope control](https://docs.composio.dev/docs/authentication/controlling-scopes), [auth-config creation](https://docs.composio.dev/reference/api-reference/auth-configs/postAuthConfigs).

Daily recurring email is not wired into Schedule. The new entry point prepares one bounded task; the fictional canary's suggestion to save a recurring pattern is not proof of scheduled email support. Actual mailbox retrieval, account/scope verification, provider throttling, revoked consent, expired connections and sustained office throughput still need live validation after the user's authorization choice. Operation receipts describe tool outcomes; they do not by themselves prove that a property-management task was completed correctly.
