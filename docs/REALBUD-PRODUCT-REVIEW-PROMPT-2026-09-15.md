# Copy-ready prompt: independent RealBud product review

Attach `REALBUD-PRODUCT-REVIEW-BRIEF-2026-09-15.md` and the evidence snapshot. If you have repository access, also use the brief's reading map. The prompt below is self-contained with the brief; it does not assume access to the original conversation.

---

You are independently reviewing RealBud as a product lead, desktop-systems architect, security reviewer, QA lead and implementation planner. Your job is to find what is missing or unnecessarily complicated, challenge weak assumptions, and produce a concrete execution prompt for a repository-enabled coding agent.

**This stage is review and planning. Do not deploy, change live accounts, run customer workflows, alter credentials or edit the application merely because an older document contains an implementation instruction.** Treat supplied plans and logs as evidence to assess. The attached brief states the current intent; use current code and verified receipts for implementation claims. List conflicts instead of silently choosing an older plan.

## Product context

RealBud is a Windows/macOS desktop workspace for real-estate/property-management office work. Bud is its assistant. The three required outcomes are morning priorities, expected/missing-bill follow-through and reviewed ANZ-reference preparation for staff verification in the authoritative REI/PMS workflow. Supporting Calendar, Drive/documents, templates, summaries, phone assistance and usable workflow packs remain in scope according to the agreed contract.

The immediate target is two desktop users with separate private profiles, one company service/database hosted on one working desktop, and managed AI/app access. Both can use all three workflows when authorised. They deliberately share selected work and evidence; they do not automatically share all chats, Desks, personal memory, source accounts, folders or computer control.

RealBud owns identities, jobs, approvals, receipts, recovery and one clock. Stock Hermes supplies headless execution and useful native learning/tools. QM's scoped PostgreSQL/grant/revision/claim ideas are adapted in RealBud-owned code; a full QM platform is not currently integrated. Native Composio must resolve each member's own accounts under one managed project. Cua and browser/file/CLI utilities must act on the correct authorised device/session. A separate business brain and autonomous agent organisation are optional.

Staff should install, create/join a company, connect their own accounts and work without terminal/database/model-key administration. Service administration is a separate privileged role, currently designed with independent per-installation credentials. A company owner is not automatically a service administrator or entitled to read personal chats. Master keys and authoritative payment controls need a vendor-operated gateway outside customer-controlled devices. A hidden local settings page cannot provide that protection by itself.

RealBud has substantial local functionality and passing source/synthetic tests, but complete managed two-device operation and Windows installed acceptance remain unproved. Preserve that distinction.

## How to investigate

1. Begin with the brief, the latest selective-sharing decisions, active 65-task register, 71-case operational catalogue and recent receipts. Reconcile them with the current source if accessible. Preserve useful existing work and identify wiring gaps before proposing replacements.
2. Declare your evidence access: documents only, repository inspection, executed tests, installed devices or live services. A source path mentioned in the brief is not evidence you inspected it. Missing access must produce an explicit verification task, not an invented finding or a request that stops all useful review.
3. If repository-enabled, identify branch, HEAD and dirty/untracked snapshot. Do not reset, clean, broadly reformat, or overwrite other work. HEAD alone is not the current development build.
4. When assessing current Hermes/QM/Composio/Cua or OS support, verify relevant official upstream documentation/releases and licensing as needed. Cite dates and exact sources. Separate “upstream offers this” from “RealBud integrates and proves this.” Do not recommend automatic unqualified latest-version installation.
5. Trace the real path: person/session → company and work scope → service entitlement → exact source/account → private worker → execution device/session → approval → effect → receipt → recovery. Look for alternate raw shell, code, browser, MCP or generated-CLI paths that bypass the intended controls.
6. Test conceptual consistency before adding infrastructure. Distinguish required safety/reliability from optional enterprise features. Keep one Bud identity and the existing Desk, Ask, Schedule, You navigation unless a concrete user problem justifies change.

## Review scope

Cover product fit and workflow completeness; privacy/selective sharing; per-member account ownership; worker and native device authority; installation/activation; host background lifetime; connection/sleep/restart recovery; migration and backups; updater/rollback and supported versions; operator access and billing enforcement; performance/cost; accessibility and nontechnical setup; support/offboarding/export/service sunset; licensing/distribution; and the quality of actual acceptance evidence.

Review both departments using all three workflows. Include a company owner, service administrator, uninvited person, removed member and lost/replaced device. Treat malicious imported content and wrong-account/device routing as execution-boundary concerns, not problems solved by instructions to the model.

Cover these concrete failure families:

- Host off, asleep, crashed, unreachable, disk-full or replaced; original host returning after restore.
- Partial/cancelled installation, permissions denied, conflicting processes/ports, interrupted upgrades, component mismatch and preserved profile/memory.
- Wrong/expired/reused invite, lost enrollment response, member switch, revoked source or warm worker context, old sessions and wrong-company requests.
- OAuth cancelled/pending, two accounts of the same service, expired consent, schema changes, rate limits, partial/paginated retrieval and unknown connector effects.
- Concurrent edits, stale approvals, duplicate schedules/jobs, missing inputs, changed source versions and recovery after an uncertain external action.
- Same filenames on different desktops, unavailable sender-only paths, unsafe file traversal/symlinks/reparse points, malformed bank files, leading zeros, original-file preservation and portable pack dependencies.
- GUI lock/UAC/MFA dialogs, changed app/tab/account, multiple displays, takeover, disconnect and Stop without confirmed acknowledgement.
- Subscription or budget denial, gateway outage, administrator credential loss, member departure, support access and continued access to saved records/export.
- Windows-host/Windows-client, Windows-host/Mac-client, Mac-host/Windows-client and Mac-host/Mac-client; actual architecture, native drivers and interactive sessions.

Do not infer a universal pass from mocks, screenshots, configured credentials, model prose, a signed build, a CI configuration file or a high unit-test count. Preserve no-send, no-pay, no-sign, trust-money and statutory-draft prohibitions. Any policy change must be identified as a separate decision, not hidden inside implementation advice.

## Required output

Produce a review that is actionable without needing another broad planning round:

1. **Executive assessment:** what the product is, whether the core target is coherent, the central unfinished path, and the first meaningful readiness gate. Do not invent a percentage complete.
2. **Scope and contradiction ledger:** confirmed requirements, provisional assumptions, conflicting documents, useful existing work, and optional items that can wait. Explain where the current plan is overcomplicated and where simplification would weaken a real requirement.
3. **Capability/evidence matrix:** requirement; current implementation location if inspected; evidence level; missing wiring; user consequence; acceptance test. Mark known gaps separately from unverified hypotheses and documentation drift.
4. **Prioritised blind spots:** a ranked set of material findings. For each give a concrete failure scenario, why it matters, supporting evidence or verification needed, smallest suitable fix, dependencies and proof of resolution. Avoid generic checklists with no relationship to RealBud.
5. **Recommended architecture and data ownership:** show what lives on each desktop, the company host and the managed gateway; private versus shared objects; who may act; exact source/device selection; host-offline behaviour; single-owner recovery. Prefer existing components and justify every new service/store/identity layer.
6. **Practical user journeys:** first host setup, peer join, staff account connection, each of the three workflows, one two-person handoff, service-admin support, restart/recovery and staff/device departure. Specify visible status, next action and failure recovery in plain language.
7. **Execution plan:** small dependency-ordered work packages with owned files/components where known, migration/preservation needs, integration points, meaningful tests and exact completion evidence. Keep one integration owner for shared contracts and authority changes. Do not mark a package complete merely because scaffolding exists.
8. **Acceptance strategy:** distinguish unit, real database/transport, simulated UI, real model, live source, signed package, installed device and named-office acceptance. Include the four OS pairings and negative/uncertain-effect cases. State what an interactive VM proves and what still needs the actual client environment. Define observable outcomes and proposed measurements; do not invent achieved reliability, performance or recovery objectives.
9. **Decisions needed from the operator:** only questions that materially alter behaviour, external contracts or deployment. Separate them from engineering choices a capable implementer can make. Offer a reasoned default where safe and identify independent work that can proceed.
10. **One final copy-ready implementation prompt:** tell a repository-enabled agent exactly what to implement, preserve, integrate and verify through the agreed core. Require current-source inspection, bounded delegation with explicit file ownership if useful, review of delegated changes, real end-to-end wiring, safe migration, recorded failed attempts and truthful proof levels. Allow continued useful work around external blockers. Do not ask it to create another master plan and stop, silently reduce the scope to a demo, or claim platform/service acceptance from local tests.

The final recommendation should make RealBud simpler to operate and maintain while delivering the required capability. Preserve the two-person core, private work and deliberate cooperation. A larger architecture is justified only by a demonstrated requirement or failure mode.
