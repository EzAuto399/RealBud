# website/ (Next.js portal) conventions

- Tests: `npm test` runs `node --experimental-strip-types --test lib/*.test.mjs` (the flag is required). `test:*-db` scripts start a disposable local PostgreSQL with `initdb`/`pg_ctl` (`REALBUD_TEST_POSTGRES_BIN`); `qa-*.mjs` renderers need `PLAYWRIGHT_MODULE` and write to `outputs/<topic>-<date>/`. The harness in `scripts/testing/command-site.mjs` fakes only the PostgREST transport; authority stays in SQL RPCs, so never stub an RPC to make a test pass.
- Two unrelated databases: `db/schema.ts` is Drizzle sqlite/D1 for enquiries; `supabase/migrations/*.sql` is hand-written PostgreSQL for the portal. Never apply one to the other.
- The website and the company host are separate authorities: the website proves online identity only; membership and case authority are checked independently by the company host. A browser body never carries `companyId`, actor, role, customer ID or issuer; scope comes from the server gate. The redeem endpoint is session-less and accepts no caller-supplied actor.
- Sessions are HMAC-signed cookies with an exact field list; `identityEpoch` is re-checked on every call, so never cache the person. Use `requirePortalPerson` for sensitive operations, not `getSessionAccount`. Never reuse the Supabase client that verified an OTP for a service-role RPC. The company-portal admin client allowlists exact RPC pathnames; adding an RPC means editing that allowlist.
- Mutations require a same-origin `Origin` plus `application/json` and a byte-bounded body; all portal JSON goes through `privateJson` (`no-store`); error text is a fixed user-facing map, never a raw RPC message.
- `next.config.ts` roots at the repo parent because the site compiles the sibling `shared/` contracts; this is not a standalone checkout. `vinext`/`build:sites` is the legacy Sites path, not production. `website/AGENTS.md` is regenerated by `next dev`; keep the generated block rather than deleting it.
