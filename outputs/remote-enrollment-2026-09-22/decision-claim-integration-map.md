# Protocol 2 review, decision and claim integration map

Read-only preparation, 22 September 2026. Only this report was written. The map follows current source and the earlier [remote approval plan](/Users/yoda/projects/RealBud/outputs/skill-history-2026-09-22/remote-approval-next-plan.md); it does not claim new review upload, remote decisions, execution, deployment or provider access. The earlier plan's email-only identity and missing-enrollment descriptions are now historical: stable people, attended enrollment and local disclosure approval exist.

## Smallest complete next implementation

Complete one protocol 2 request lifecycle for **both existing preparation adapters**: an authorized portal request reaches the correct running desktop; the desktop publishes the complete previously approved disclosure for that exact request; an explicitly enrolled audience member reviews it and commits a decision; the desktop obtains an online claim and runs the existing executor; durable status returns to the portal. Local rejection/cancellation and any supported local approval must arbitrate through the same authoritative decision/request revision. Keep the existing private result storage and separate downstream approvals.

This requires request submission/inventory, review publication/read, decision, v2 polling/claim/events, desktop recovery and rendered portal review together. A review upload endpoint or a saved remote decision alone is not completion. No parallel worker/executor is needed. The current `morning-review` and `prepare-recipe` adapters remain the execution implementations; bank posting, REI submission, sending mail, arbitrary Ask execution and shared-department execution are not accidentally enabled through them.

Add request-linked review/decision records with immutable identities, exact JSONB replay bodies and a durable current-review/winning-decision CAS. Their names and exact wire shapes are new design work, not existing functions. Store the complete approved projection once, separately from small decision/claim receipts. Private execution binding stays in the desktop's encrypted DB. Compare canonical projection digests consistently in shared code; exact JSONB comparisons in SQL must not depend on a different SQL serialization hash.

All relevant mutations must follow **global identity → company → installation → current account → parent → enrollment(s) → request → review/decision → claim/event**. Lock multiple audience enrollments in a deterministic order. Existing global serialization is not a reason to omit row locks or invert the future order. New tables should follow the enrollment table's direct-service denial and security-definer RPC boundary, not copy the older broad service-role table grants.

The complete current-review binding must include request/envelope identity, parent generation and opaque worker binding, unique review incarnation, private preview digest/revision, descriptor revision, exact template digest, explicitly frozen audience enrollment IDs/generations/subject epochs, complete projection/digest and fixed expiry. A changed source, instruction, template, audience, parent or worker invalidates that review. Content A→B→A does not restore a consumed decision; monotonically versioned or fresh review identity is necessary.

One decision slot per current review revision arbitrates all enrolled people and any supported desktop-local approval. The first valid approve/reject wins under SQL CAS. Identical UUID/body retry returns the same receipt; a competing person, changed body or old revision conflicts. Approval is “waiting for the computer” until a current online claim is committed. Do not fabricate a portal person for an attended local decision; its separately defined desktop authority must join the same CAS.

At claim, recheck requester admission, current parent/installation, enrolled approver identity/epoch, latched stale/revoked/expired state, scope/template, current audience/review, winning choice, cancellation and all deadlines **before a replay receipt is returned**. An old claim ID cannot renew its lease. An approved review alone cannot be enqueued while offline. After the claim, the existing local `check` and synchronous adapter guard remain necessary; server authority does not validate current private files or connectors.

## Recovery, compatibility and retention

Reuse [restoreWebsiteRequest](/Users/yoda/projects/RealBud/server/website-requests.ts:92), [restoreRemoteTemplate](/Users/yoda/projects/RealBud/server/website-remote-disclosure.ts:20), [restoreRemoteEvidence](/Users/yoda/projects/RealBud/server/website-remote-evidence.ts:16) and the existing graph validation in [server/website-work-backup.ts](/Users/yoda/projects/RealBud/server/website-work-backup.ts:1). Extend their strict admission for new versioned request/review evidence. In [server/private-workspace-backup.ts](/Users/yoda/projects/RealBud/server/private-workspace-backup.ts:406), restored work is rekeyed, marked historical/interrupted and denied execution; schedules remain off. Never restore report/command credentials, pending upload authority, an executable decision or a reusable claim. Re-export must preserve historical links without making them live.

Publication needs a saved immutable local outbox before upload and an exact receipt before marking it delivered. A lost upload reply retries the same review, projection and audience. A changed template requires a new locally approved template and review; it cannot mutate an old upload. Keep audit/decision IDs when deleting disclosed content under an explicit bounded retention policy. The earlier plan's proposed seven-day post-terminal retention is still a proposal, not an implemented guarantee; SQL/database backups require a separate honest policy.

Crash after saved claim intent but before enqueue reconciles the existing executor key. No run means interrupted and fresh review/decision is needed; an existing run is reattached, never duplicated. A crash after enqueue must not depend on a separate new executor journal. Lost terminal replies retry the original event; running/terminal ordering and stable `runReference` remain consistent with `flush`.

Keep the v2 downgrade marker and permanent SQL floor. Old clients cannot interpret new records as unapproved local work, missing authority cannot default to v1, and restoring old local files cannot re-enable old credentials or bypass v2 decision requirements.
