### Exact diagnosis of the current refusal (source only)

- `a8938b1:managed-gateway/key-gateway.ts:152–171`: project key and account ancestry are checked, then billing tenant `active && serviceExpiresAt > now && goLiveAt <= now` throws **service_unavailable** before `activeCard` is read. A missing tenant would instead say `tenant_unavailable`; inactive client/customer/project would say `account_inactive`. Thus the observed exact error identifies the billing tenant eligibility check, not the rate-card query.
- Read-only mapping: GET `/v1/operator/clients` and `/v1/operator/customers`; choose billingCompanyId from the payer rule in `accounts.ts:131`. GET `/v1/operator/status` returns `tenants[].companyId`, computed `active`, `serviceExpiresAt`, `includedUntil` (`console.ts:92–104`). Filter output to the fictional mapped company. It omits raw active/goLiveAt; for a platform tenant `includedUntil === goLiveAt` is enforced at provisioning (`ledger.ts:41`). There is no GET billing-account detail route; `/v1/operator/billing-accounts` is insert-only POST. Internal `ledger.setService` exists (`ledger.ts:55–58`), with no HTTP renewal route exposed in this revision.
- GET `/v1/operator/rates` directly calls `ledger.cards()` (`platform-admin.ts:311–312`), whose only work is `SELECT body,digest FROM cards ORDER BY id` followed by JSON parse (`ledger.ts:89`). `activeCard` uses a different join against acceptances and produces `rates_not_accepted` when empty (`ledger.ts:92–96`). **Status also calls cards** (`console.ts:104`), so a status 200 alongside rates 502 does not establish a persistent common cards failure. The next diagnostic is matching revision/timestamps plus a sanitized server-side exception type/code or a read-only rate query diagnostic; no source-supported root cause is yet established. HTTP intentionally maps every non-GatewayError to 502 request_failed (`http.ts:475–476`) without leaking its message/body.
