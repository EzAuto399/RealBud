## First required protocol-2 boundary

A functioning challenge attached to an unchanged protocol-1 grant is not the planned remote authority contract. First establish an explicit protocol-2 command grant with remote capability negotiation and a new generation/token. Preserve old grants and requests as historical/local-only; require an attended transition rather than silently upgrading permissions. The existing active-workspace unique index (`202609220001_installation_commands.sql:13`) means replacement of a v1 grant must be deliberate and reconciled, not a second active grant with the same target.

If the existing command tables are reused (the smallest change to existing installation/grant authority), add strict protocol partitioning in the same migration that admits v2:

- `realbud_submit_command` currently has **no grant protocol check** and always constructs a protocol-1 envelope (`:103–122`). A new v2 grant accepted into that table would otherwise allow this old endpoint to produce a legacy request under new authority.
- `realbud_claim_command` checks exact request/envelope identity, but is not a v2 approver check (`:135`). It must explicitly reject a v2 grant/request before any claim receipt or transition.
- Audit v1 poll, ack, revoke, account catalog and owner submit/cancel paths together. The v1 catalog parser rejects v2 objects, so keep old catalog output v1-only and surface v2 through its own endpoint. Do not treat a parse failure as permission to retry via v1.
- A v2-aware local `grant.json` admission must remain a durable downgrade gate. An older app's current exact `version:1` validator (`server/website-requests.ts:93`) should hold, never ignore remote constraints or overwrite them during fresh v1 enrollment.

Alternative physical separation into dedicated v2 tables can provide this partition inherently, but must still share parent-installation revocation and avoid two effective grants for one target. Decide that storage detail once before parallel edits; do not ship a partially partitioned mixed table. This report recommends the explicit versioned existing-table approach with the listed rejection tests, preserving the existing transactional authority patterns.

## Minimal vertical enrollment state machine

Use a new `shared/website-remote-approvers.ts` (proposed filename) for exact v2 challenge, candidate, confirmation, grant and revocation receipt contracts. Keep opaque worker binding separate from the full local worker identity. Hash shared canonical JSON using the existing canonical encoder; SQL compares exact immutable JSONB bodies rather than independently guessing the JavaScript digest serialization.

1. **Begin locally:** under the existing authenticated local session, select the eligible operation descriptors and disclosure policy, freeze parent grant/generation + installation/company/workspace/full worker authority, create random enrollment/challenge IDs and 32-byte secret, and durably save the immutable begin intent before HTTP. Publish only the secret hash. A successful begin receipt is still pending, not authority.
2. **Accept on portal:** freshly authenticated v2 person enters the challenge. SQL rechecks current stable identity in the same transaction, active installation/parent v2 grant/company, expiry, challenge hash and attempt capacity; it saves one exact candidate subject/provider/account/epoch. Candidate is pending. Challenge possession alone cannot activate a grant. Identical acceptance retry is idempotent; another candidate or mismatching body conflicts.
3. **Review locally:** outbound authenticated status returns the authoritative candidate. The local screen shows verified person email/account, company, exact target workspace/worker description, allowed operations, disclosure categories/templates and expiry. Pin the entire candidate digest and local revision; a changed identity, parent grant, worker or policy clears confirmation.
4. **Confirm locally:** persist the exact candidate confirmation/outbox before network. SQL rechecks all active relationships, candidate identity epoch, expiry and exact immutable body; creates a separate approver grant ID/generation and returns an immutable receipt. A lost response is recovered by exact retry/status. Local state becomes active only after the matching committed receipt is saved and local authority is checked again.
5. **Revoke:** persist local disabled state before outbound revocation. Retain only the material necessary for exact revoke retry. Remote revoke must deny new portal reads/decisions/claims immediately, including when desktop is offline; the desktop learns it on its next authenticated sync. Parent command disable/disconnect invalidates all subordinate grants. Renewal is an attended new generation, invalidating old review authority.

Suggested existing-plan defaults remain **proposals requiring central constants and boundary tests**: ten-minute challenge, thirty-day approver grant. Set a bounded fresh-authentication window for challenge acceptance using signed `authenticatedAt`; the seven-day cookie lifetime is not an attended enrollment freshness policy. Confirm exact defaults as a reversible implementation choice in the next specification, not scattered literals.

## Durable integration and recovery

Keep usable secrets/live enrollment authority in a new private credential state file beneath `website-requests/`; the current backup path allowlist excludes that whole authority area (`server/private-workspace-backup.ts:38–76`). Use `readPrivateJson`/`writePrivateJson`, strict version and capacity admission, exact immutable IDs, and the same host activity/restore barriers. Maintain historical enrollment evidence without the challenge secret or usable credential in encrypted workflow records. Do not simply add secret-bearing records to `WorkflowDatabase`: backup enumerates the whole workflow database and currently rejects unknown kinds (`private-backup-capture.ts:335`, `private-workspace-backup.ts:241`).

For a separate historical record kind, add exact logical-record validation in `private-workspace-backup.ts`, graph admission in the common catalog path and v1 path, plus restore transforms. If evidence is embedded into the future v2 website request record, extend that record's exact versioned validator and current `website-work-backup.ts` graph instead. Either way, preserve request→enrollment grant generation→review→decision→run linkage without restoring authority.

Existing relevant restore seams:

- `server/private-workspace-backup.ts:248`, `:294`, `:402`: exact record admission, graph validation and v1 restore transformation.
- `server/private-backup-catalog.ts:334`, `:459`: shared logical validation and graph verification for v2 capture/import.
- `server/private-backup-restore-catalog.ts:173`: streamed restore calls `restoreWebsiteRequest` and increments revisions.
- `server/website-requests.ts:87`: restored records clear intent/outbox, interrupt unfinished work, preserve run evidence and set `restored:true`.
- `server/index.ts:4957`, `:4971`, `:5015`: idle admission, fresh destination checks, stop/restore coordination. Add enrollment activity and authority files to these checks, not just its HTTP UI.
- `server/private-backup-website-requests.test.ts:55`: real encrypted v1/v2 fixtures already test excluded command/report credentials and inert restored history. Extend these fixtures for secret exclusion, interrupted enrollment publication/confirmation, removed destination authority, re-export and fresh independent enrollment.

Do not restore any usable challenge, pending confirmation/publication, live approver grant or accepted-but-unclaimed decision. Historical immutable identities may remain as evidence but must be explicitly inert. Restore must not republish content or acknowledge old authority. A restored workspace UUID does not reactivate enrollment.

## Lock order to settle before SQL implementation

The existing command authority takes company advisory lock, installation row, current owner SHARE lock and grant row (`202609220001_installation_commands.sql:44–62`). The newly added identity assertion takes the global `realbud_portal_people` advisory lock; billing mutation triggers take that lock at statement start (`202609220002_portal_people.sql:45`, `:174`). Thus future RPCs need an agreed order including **identity lock first**, then company command lock, installation, parent grant, enrollment/approver grant, request/review. Do not call identity assertion after acquiring a reversed command/row order. Include account-disable/move, parent revoke, candidate accept/confirm and concurrent command paths in actual PostgreSQL tests. Use the identity helper's admitted READ COMMITTED transaction contract; unsupported isolation is deliberately held.

Enrollment requires at least three service-only durable SQL objects: challenge/pending candidate, approver grant, exact mutation receipt (or equivalent immutable body/receipt fields). All must enable RLS and revoke public/anon/authenticated access. Reuse bounded errors but add explicit stale/challenge-used/expired/recovery outcomes as needed. Store hashed challenges only. Rate limits/capacity must bound failed attempts and historical replay receipts without deleting replay fences that permit reuse of old IDs.

## Proposed disjoint ownership and implementation order

1. **Root contract pass:** exact shared v2 types/parsers, durable version admission, centralized expiry/freshness constants and protocol partition tests. Freeze these signatures before assigning parallel production ownership.
2. **SQL/website domain owner:** new migration; service-only begin/accept/status/confirm/revoke functions; exact actor assertion; v1 partition guards; account/browser and installation routes; actual PostgreSQL race/replay/identity tests. Do not modify the core session implementation unless a demonstrated integration defect requires it.
3. **Desktop domain owner:** new enrollment module/private state and tests, shared parent coordinator seam in `website-requests.ts`, typed transport additions, synchronous current-authority accessor from `website-work-adapters.ts`. Own no renderer or backup files.
4. **Root integration/UI/backup owner:** route wiring and lifecycle/activity/restore hooks in `server/index.ts`, local enrollment/recovery UI in or beside `WebsiteRequestsCard.tsx`, portal accept/current-grant view, both backup paths and actual Next→desktop dual-party fixture. A reviewer owns no production files.
5. **Next vertical:** attended disclosure template projection for both adapters, upload/read privacy boundaries, review/decision CAS (including competing local/remote decisions), v2 claim integration into the existing executor. Enrollment alone is not remote approval and must not be labelled executable authority in the UI.
6. **Required follow-on:** the separate company-member/department scoped delegation and fenced case adapter from the full plan; never manufacture department execution by adding a department ID to the private adapter.
