# Department integration: next implementation map

Source inspection on 2026-09-22. This report changes no product code or database. The separate protocol 2 SQL receipt proves the private workspace lifecycle at its recorded hash; it does not prove shared department execution. The current desktop/website integration is still being verified by the parent task. No tests were rerun for this read-only map.

## Current boundary

RealBud already has two distinct authority systems. The website uses stable portal people, installation/parent grants, explicit enrolled approvers, reviewed disclosure and online claims. The company host uses authenticated company members, department scope grants, case assignments and lease fences. These identities must be connected explicitly; a billing company ID, office label, portal role, local worker profile or shared email is not that connection.

The current [RemoteWorkEnvelope and review contracts](/Users/yoda/projects/RealBud/shared/website-remote-work.ts:12) identify the website company, installation, workspace, worker binding, requester enrollment and descriptor. They contain no company-host member, department, case ID or case fence. [Remote enrollment preparation](/Users/yoda/projects/RealBud/server/website-remote-approvers.ts:151) binds the local workspace and approved descriptors, not a department membership. [Workspace identity](/Users/yoda/projects/RealBud/server/workspace-identity.ts:24) can derive its worker member key from a saved seat, but that is a durable local identity, not a fresh company session or scope authorization.

Consequently, the completed SQL lifecycle can authorize a reviewed preparation on its specific local workspace. It cannot yet claim that the preparation runs under the company host's department permissions or owns a particular department case. Giving a workspace a department name would not close this gap.

## Smallest maintainable complete next slice

Start with one explicitly selected department and an existing assigned case, using `prepare-recipe` through the current executor. Keep both current private adapters operational. Leave `morning-review` in its current private workspace scope until there is a reviewed department-specific connector/source binding; a department label cannot make the private inbox safe to share. This is a bounded department integration slice, not a claim that every workflow is department-aware.

1. **Define the authority bridge before changing the work envelope.** Add a versioned, attended binding between the stable portal person and an authenticated company-host member, plus the target host/company/department and executing seat. Persist a nonreusable binding incarnation and relevant department revision. Verify both sides; do not infer membership from email, `billing_accounts.company_id`, role, company name, or a seat file. The requester, remote approver and executing seat may be different people; each required role needs its own explicit permission. The case holder must remain the authenticated executing member, not an impersonated remote approver.
2. **Add a discriminated target binding.** Extend shared contracts and persisted execution records with a new explicitly versioned department target, preserving existing private records. The public projection can include approved department/case display metadata and opaque binding identifiers. The private execution binding carries exact host identity, company/member/scope IDs, department revision, case ID, case fence and private claim reference. These are proposed fields, not existing authority. New target changes invalidate old previews/decisions and require new immutable work IDs; do not overload an existing private review with different scope.
3. **Use company-host admission under its existing transaction policy.** Reuse `authenticated`, `authorizedScope`, `lockedCase` and `currentClaim` to admit and validate a scoped execution binding. Add a read-only current-claim check or a dedicated bounded admission operation that validates membership, assignment, non-retirement, expected department revision and case fence without silently renewing ownership. Existing `renewClaim` explicitly renews a live company lease; it must never be used to extend the separate fixed website claim or to recover an expired case automatically.
4. **Compose both permissions at every execution door.** The website's person/enrollment/decision/claim and the company's member/department/case authority are independently required. Extend `WebsiteRequestExecution`, the saved remote-work record and `createWebsiteExecutionContext` so losing either permission holds new source/provider operations. The adapter must select only scoped case/knowledge data for the chosen department. Retain the actual executor's durable enqueue and lookup key. Member disable, scope change, case reassignment, company disconnect, worker/host switch and subscription denial must synchronously invalidate the local continuation before another provider entry.
5. **Reconcile real outcomes through existing cases.** Bind the remote request/decision/claim to an audited company receipt and the actual local run. A lost response must find the same receipt/run, never acquire another case or repeat an effect. After a started run loses scope permission, report the factual local outcome and use explicit department recovery; do not automatically mark the case done or release it under a stale fence. Persist result linkage separately from any projected customer content.
6. **Expose the actual target and permission state.** Local setup should choose an authenticated department, case, executing seat and reviewed source. Website review should clearly show that target and whether execution is waiting for the office host, case ownership, remote review, or recovery. An unavailable company host must hold protected shared work and sensitive reads rather than falling back to a private workspace or an owner-wide default.

### Transaction boundary that must be decided explicitly

The website Supabase schema and the optional company PostgreSQL host are separate authorities. Their advisory locks do not form one transaction. A successful portal claim plus a cached department check does not establish atomic cross-database revocation. Before implementing the bridge, define the final company-host effect-admission operation, exact receipt/retry protocol and maximum lease exposure. If both authorities cannot be freshly verified, fail closed for new scoped effects. Do not describe a two-request client sequence as atomic, hold an unbounded database transaction across provider execution, or promise instantaneous provider cancellation after an already admitted external effect.

A practical implementation can use short, immutable website claim evidence plus company-host transactionally validated case admission, followed by the existing local continuation fence. But the exact trust channel for the host to verify website evidence and the rule for a revocation between those steps still need a concrete design and race tests. The browser must not be able to submit a self-asserted “current member” or “approved receipt” object and have it treated as authority.

## Credentials and commercial controls remain separate

[Managed service provisioning](/Users/yoda/projects/RealBud/server/managed-service.ts:21) reads trusted company/host policy and keys from private configuration, never from an HTTP body. [Service entitlement verification](/Users/yoda/projects/RealBud/server/service-entitlement.ts:109) explicitly states that the local signed check is not a billing service, live revocation service or protection against host administrators. [The actual adapter admission](/Users/yoda/projects/RealBud/server/index.ts:4967) calls `managedService.assertCapability('reasoning')`.

[Managed connector configuration](/Users/yoda/projects/RealBud/server/managed-connectors.ts:5) uses a private service credential/profile, while [service admin gating](/Users/yoda/projects/RealBud/server/care-unlock.ts:21) controls credential editing. Department membership should neither expose these credentials nor allow a department administrator to replace LLM/Composio service policy. Conversely, paying a subscription or possessing a billing role must not grant access to another department. The hosted provider/connector service must continue enforcing its own tenant, capability and commercial limits; local UI locks alone do not guarantee a non-paying host administrator cannot use copied credentials.
