# Windows signed-memory persistence recommendation

Date: 2026-09-22. Scope: design review and admitted-source inspection only; no production edits, Windows execution, personal profiles, or platform-hold changes. Grok findings will be recorded separately. Microsoft API documentation is evidence of requested behavior, not a successful Windows runtime test.

## Recommendation

Implement one strict Windows HANDLE persistence primitive around `SetFileInformationByHandle(FileRenameInfo)`. Keep the verified source HANDLE open from creation/read through rename and verification; use a verified destination directory HANDLE with a generated relative leaf. Use no-clobber publication for new immutable records and claims, intentional replacement only for existing mutable memory/receipt state under the native cooperative locks. Require checked file flushes before and after publication and request write-through when opening the source. Never call Hermes' copy/in-place fallback for signed state or final memory publication. Keep the Windows feature hold until real Windows validation establishes the narrower supported behavior.

This is the smallest source-identity-safe design among the requested alternatives. It does **not** turn replacement into a compare-and-swap on the old destination, or make a multi-file journal a transaction. Public Win32 documents relative `RootDirectory` and replacement behavior; its currently rendered struct includes duplicated union fields, so use the SDK ABI and test both supported architectures. [FILE_RENAME_INFO](https://learn.microsoft.com/en-us/windows/win32/api/winbase/ns-winbase-file_rename_info), [SetFileInformationByHandle](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-setfileinformationbyhandle).

## Operations

| Operation | Minimum sequence | Error or interruption behavior |
| --- | --- | --- |
| New signed intent/proposal/immutable result | Create unique same-volume staging with `CREATE_NEW`, private DACL, read/write/delete access, write-through; validate handle; write all bytes; checked `FlushFileBuffers`; rename by that handle with `ReplaceIfExists=FALSE`; checked post-rename file flush and identity/HMAC verification. | An existing destination is a collision/reconciliation case, never permission to overwrite. A failed/ambiguous publication is reconciled from signed disk state. |
| Memory/final-receipt replacement | Same staging sequence, native sibling target lock plus review lock, exact current context/digest check, `ReplaceIfExists=TRUE` only for the intended mutable record. | Sharing/lock/access failure preserves journal and reports busy/recovery. No copy or truncate. Replacement has a destination-name race against writers that ignore the lock. |
| Exact pending cleanup | Open the pending object with read/delete access, deny write/delete sharing; verify private ACL, regular type, link count and exact digest; rename that HANDLE into a no-clobber claim; verify claim identity; dispose by the same handle; close; reconcile name absence. | Leave final signed receipt until cleanup is proven. A live-name recreation is a conflict and must not be deleted. A crash after claim but before delete resumes only the exact claim. |

No `FILE_ATTRIBUTE_TEMPORARY` or automatic delete-on-close on recoverable state. A zero-byte/partial write is an error. Do not convert an unsupported flush into success. Parent and child admission must complete before reading or writing private contents.

Use `GENERIC_READ | GENERIC_WRITE | DELETE | READ_CONTROL` as needed on new staging; deny WRITE and DELETE sharing. Permit read sharing only if required. A verification read handle opened while the source's write/delete handle remains live must itself advertise compatible READ/WRITE/DELETE sharing while requesting only read/metadata access. This does not weaken the original handle's denial of new write/delete access. Obtain directory handles with backup semantics, traverse/read-attribute/security access as needed, sharing READ|WRITE but not DELETE. The WDK documents the internal rename target-directory open; denying WRITE sharing on the parent can cause a self-inflicted failure. [CreateFileW](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-createfilew), [FILE_RENAME_INFORMATION](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/ntifs/ns-ntifs-_file_rename_information).

Readback through the retained source HANDLE is preferred and requires no broader source sharing. After an acknowledged successful rename, that same deny-delete handle continues to pin the published object; a second pathname open is not mandatory merely to recompute its HMAC. On an ambiguous rename result, source bytes alone do not prove which name was published: recovery must reconcile the intended destination and signed state. The compatible-share reopen above is only an optional identity check, not a requirement to loosen the original source handle.

Compare volume serial and file ID from live handles, not canonical path strings. Keep the source handle live; identifiers persisted after deletion are not permanent identity authority. Restrict names to generated leaves without separators, colon/alternate streams, dot components or device syntax. Do not fall back to a path rename when the handle API or filesystem rejects the operation. [FILE_ID_INFO](https://learn.microsoft.com/en-us/windows/win32/api/winbase/ns-winbase-file_id_info).

Handle disposal marks deletion; closing the final handle matters. A successful disposition call alone is not proof that the name is absent. Keep ordinary deletion semantics; POSIX replacement/delete flags that bypass open-handle behavior are unnecessary complexity for this scope. [FILE_DISPOSITION_INFO](https://learn.microsoft.com/en-us/windows/win32/api/winbase/ns-winbase-file_disposition_info), [DeleteFileW](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-deletefilew).

## Why not the alternatives

`MoveFileExW` with same-volume paths and without `COPY_ALLOWED` can request no-clobber or replacement and `WRITE_THROUGH`. Its documentation says it waits for the move to disk, but the detailed flush guarantee describes copy/delete. It does not establish the source HANDLE identity or cross-file ordering needed here. Reopening source paths weakens the identity binding; retaining a deny-delete source handle makes a separate path-based DELETE open problematic. There is no reason to introduce this second rename path as fallback. This is a design preference, not a claim that Microsoft ignores WRITE_THROUGH on same-volume moves. [MoveFileExW](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-movefileexw).

`CreateHardLinkW` then unlink is not the minimum safe publication path. It adds a crash-visible two-link state that current admission rejects, and the API is path-based. A destination link shares the source file's security descriptor; it does not gain a separate safe ACL through destination inheritance. Supporting this path would need explicit link-count and cleanup recovery states without improving the required handle binding. [CreateHardLinkW](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-createhardlinkw).

## Crash and power-loss claims

For a **process crash**, a completed same-volume rename survives in the running OS namespace; staging avoids exposing partially written target bytes. Recovery still needs termination tests immediately before/after intent publication, memory rename, final receipt publication, claim rename and claim deletion. Exact signed identity plus before/after digest determines recovery; elapsed time or a lost tool response never proves application. A crash in a syscall is an unknown outcome until those records are reread.

For **power loss or OS crash**, request `FILE_FLAG_WRITE_THROUGH`, flush staged data before rename, and flush the same source handle after rename. Microsoft's caching guidance describes NTFS metadata flushes including rename for write-through requests and requires flushing metadata even when buffering is disabled. That supports the API request, but does not prove our complete cross-file write ordering on arbitrary drivers, storage caches or filesystems. Hardware support varies; no-buffering also requires sector alignment and is not necessary merely to write these small JSON files. [File caching](https://learn.microsoft.com/en-us/windows/win32/fileio/file-caching), [CreateFileW caching guidance](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-createfilew).

A normal directory HANDLE is not a documented POSIX `fsync(directory)` replacement. Volume-wide flushing requires administrator access; do not silently elevate or turn a failed directory flush into a durability receipt. The relevant supported file flush must succeed and actual power-interruption recovery remains a separate admission gate. [FlushFileBuffers](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-flushfilebuffers).

## Private inherited ACLs and pinned parents

Create the protected private root with only the intended host principals and OI/CI inheritance before native children are created. Protection stops inheritance **into** that root, not its intended safe inheritance **to** children. New explicit staging DACLs may also be protected. A pre-existing child with broad explicit grants is not repaired merely by securing its parent. Query the owner, DACL and type on every opened child before private content access; reject unsafe state, or repair only through separately authorized setup. Null DACL is never private. Existing-child propagation can be limited by sharing and access mode. [SECURITY_INFORMATION](https://learn.microsoft.com/en-us/windows/win32/secauthz/security-information), [SetSecurityInfo](https://learn.microsoft.com/en-us/windows/win32/api/aclapi/nf-aclapi-setsecurityinfo).

Parent handles omitting DELETE sharing pin those directory objects against rename/deletion for their lifetime. They do not freeze child entries or stop an equally authorized owner from changing ACLs. Final-component no-reparse opens are insufficient by themselves: validate and pin relevant ancestry as well. Same-user/admin hostile-process resistance is not created by a private per-user ACL.

The replacement caveat is unavoidable with this primitive: `ReplaceIfExists=TRUE` addresses a destination name, not an already-open destination identity. Holding the old target with deny-delete blocks our own replacement; allowing delete permits uncoordinated substitution. The minimum protocol therefore assumes native cooperative locking and a private namespace, and detects observed drift. If the product requires protection against arbitrary writers ignoring the lock, claim the exact old target by HANDLE into a no-clobber backup, then publish the new target no-clobber. That is a different protocol with a missing-target crash interval and must add signed recovery before use; merely adding another pre-check is not a CAS fix.

## Actual admitted Hermes seams

Checked source at admitted commit `345cd2b057a452236de401d3534b8502a7465e8d`; exact SHA256 values are in `persistence-source-evidence.json`.

- `tools/memory_tool_store.py:145–181` locks byte0 of sibling `<target>.lock` with `msvcrt.locking(...LK_LOCK,1)` on Windows. Reuse this native lock so normal Hermes writers serialize; do not replace it with a helper-only lock. It is a cooperative lock on a particular file identity. The CRT can retry ten times at one-second intervals, so additional retries must fit the host timeout/cancellation budget. [Microsoft CRT _locking](https://learn.microsoft.com/en-us/cpp/c-runtime-library/reference/locking?view=msvc-170).
- `tools/memory_tool_store.py:418–424` calls `utils.atomic_write_text`. `utils.py:154–193` retries Windows rename contention, then writes the target in place for Win32 errors5/32/33; EXDEV/EBUSY uses copy. `utils.py:198–215` skips directory sync on Windows. These paths cannot carry our journal's atomicity claim.
- `tools/write_approval.py:73–88` does not take the review lock, uses that atomic JSON helper, and returns a record even after persistence fails. A returned native proposal record is not a publication receipt.
- Current RealBud `_write_memory` calls native `_write_file`; the Windows branch must instead save the exact already-native-rendered `after` bytes through the strict HANDLE primitive, retaining native semantics, checks and locks. The ordinary native memory runtime may still use its upstream fallback independently; this review does not claim all upstream writes become crash-safe.

## Narrow admission evidence still required

1. Actual public HANDLE rename/no-clobber/replacement with correct ABI on supported Windows x64/ARM64 and the explicitly admitted local filesystem; verify source and destination handle identity and ACL at each boundary.
2. Two real processes contending on native `.lock`, and an independently opened read/write/delete target handle; sharing failures must preserve exact old bytes and journal. Error5 must not trigger a rewrite.
3. Existing destination collision, explicit unsafe child DACL, protected parent inheritance, hardlink, ancestor/final reparse and live-name recreation; none may be silently overwritten or reported as completed.
4. Terminate the real helper at each journal/publication/claim boundary, reopen, and reconcile exact digest/decision. Include partial writes, flush failures, disk-full publication and ambiguous native results; signed incomplete state must remain recoverable.
5. Separate OS/power-loss testing if that durability level is claimed. macOS tests, mocked Win32 results, a package build and this documentation review cannot supply it.
