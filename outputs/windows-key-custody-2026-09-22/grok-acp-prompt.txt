Review this Windows key-custody design in at most 200 words. No tools or web; use only this metadata.
Context: an Electron desktop app keeps a wrapped workspace key (desk.key.wrap, plus desk.key.wrap.recovery-* copies) in a per-user data directory. On POSIX it checks mode 0600, owner uid and link count before reading, and writes temp file, fsync, rename. On Windows, mode bits mean nothing. The server side already applies a protected explicit DACL (owner plus allow ACEs limited to the current-user SID, SYSTEM and Administrators, inheritance protected) through PowerShell that receives path, kind and action as environment variables, never interpolated, and verifies existing files by comparing the DACL and refusing reparse points and extra hard links.
Proposed change: the key module receives an injectable Windows privacy helper. It restricts the key directory only when this start creates it; a pre-existing directory from an older install is tolerated, as on POSIX, because each key file carries its own protected descriptor. It restricts the temporary file before any key material is written, then renames (a protected DACL survives rename on the same volume). It verifies both existing key files before reading. Only the PowerShell exit code is kept in error text. The ACL script is a byte-identical copy of the server's, with a parity test.
Identify the most important missing assertions, any way a same-user process or an inherited ACE could still read the key, whether tolerating a pre-existing directory is acceptable, and what must run on actual Windows. Return JSON with keys verdict (string), requiredChecks (array of strings), risks (array of strings), windowsOnly (array of strings).
