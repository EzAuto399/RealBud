# Windows native memory admission: next bounded wave

Repository inventory, 2026-09-22. No production files changed, Windows hold removed, Windows command run, credential accessed, or upstream Hermes source modified. Source references were inspected in the current dirty worktree; this is a plan, not Windows acceptance evidence.

The next useful local deliverable is an owned Windows storage adapter plus a Windows-specific acceptance harness, with the product hold kept until native evidence passes. This is more than removing a platform check. Existing Windows packaging infrastructure can host the acceptance work, but it currently proves neither Hermes memory nor this proposal/review path.

## Suggested sequence and stop condition

1. Implement and locally test the owned adapter contract and Windows fixture/harness scaffolding. Keep all three production platform holds. Preserve POSIX regression receipts.
2. On an explicitly authorized disposable Windows runner, test primitive/ACL/lock contracts first. Investigate failures before running the full application fixture. Record Windows-native failures without raw paths/SIDs/content.
3. Run real native memory/fault/HTTP tests and exact installed packaged browser checks on the same source/build. Include native background pending compatibility; proposal-only synthetic files are insufficient proof of the whole native inbox.
4. Admit Windows only in a reviewed change once all required guarantees hold. If only read/list can be proved, keep mutation/proposal unavailable rather than equating partial read support with full admission. Retain runtime/hash/identity restrictions and recovery UI.
5. Report Windows CI, installed package, Windows 11 device and live customer layers separately. No Windows gate was passed by this inventory.
